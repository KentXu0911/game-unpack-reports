③ 活动礼包档位 —— 拿得到配置线索，拿不到货币金额

先给结论。 礼包价格是两层结构：🟢 第一层（已扫描客户端范围内可读） = 价格档 id / SKU / 内容物 / 6 档金币锚价； 🔴 第二层（客户端读不到） = 真实货币金额与本地化文案。 后者由 APricingStrategy 在运行时通过 PurchaseHelper.ParseProducts(商店响应) 拿到， APK 里的 p 值、常量名和 SKU 数字后缀只能当作档位线索，不是已验证的地区货币金额。要拿真实价格必须捕获商店查询响应，或查对应地区和时间的 Google Play / App Store 商品信息。

3.1 价格链：SKU 在包内 → 金额在商店

硬证据：PurchaseProduct（dump.cs TypeDefIndex 11047）是 struct { readonly string id; string priceText; string priceString; float price; string currency; }， 构造函数 .ctor(id, price, currency, isMandatory) —— 金额全部是外部传入的， 唯一入口是 PurchaseHelper.ParseProducts(string message, out …)。

3.2 客户端硬编码的 6 档金币内容量（档位不等于实价）

来自 APricingStrategy（TypeDefIndex 697）的 public const int： 常量名中的 2/8/15/30/55/100 与对应金币数可直接读到，但没有商店响应时不能把数字确认为美元或据此计算真实性价比。

3.4 四种定价策略（A/B 实验）—— 为什么同一个 SKU 价格不唯一

enum PricingStrategies（TypeDefIndex 698）：
Default = 0　·　IncreasedPrice = 1　·　 LessContent = 2　·　LessContentV2 = 3
APricingStrategy.DecidePricingStrategy() 在运行时决定用哪一套。类里有 49 个 ShopPackageConfig 字段与之对应，子类 DefaultPricingStrategy 逐个 override。
这就是「价格拿不到」的第二重原因： 即使抓到金额，同一 SKU 在不同设备上可能是 4 种组合之一（涨价 / 减量 / 减量 V2）。 脱离账号的「价格表」本身就是个伪命题——必须带账号抓。
