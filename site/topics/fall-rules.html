交换、匹配、下落与多棋盘

棋盘先处理登记与规则，再推进画面

一次交换不只是换两颗棋的坐标：程序先试换逻辑位置、识别匹配组，再结合准备状态决定消除；下落先分配目标，再推进移动。下面按原代码的关键判断解释每一步。

下列伪代码根据build 38174的ARM64机器码与元数据整理，保留本节关键分支，省略类型转换、日志和无关调用；不是原始C#源码，也不能直接代替完整运行实现。例子是按代码构造的局面。

一个格子不只记录“现在有什么”

画面上的位置与程序预订的位置可能不同。下落规划至少要区分三个登记：Current是棋子当前所属格，Next是下一段移动要进入的格，Target是规划时分配的目标关系。格子和棋子两端都有对应关系，不能只用一张“颜色数组”表示移动中的棋盘。

例如，A正从上方落向空格C，B也在附近。画面上C还没被A占满，但A已经登记目标；后续规划不能直接把C当成可供B抢占的自由空格。反过来，清理旧目标也要保留已被Next预订的关系。［B1］

例子：一行原来是“红、红、蓝”，第三格下面有一颗红棋。把红棋换上来，临时逻辑行变成“红、红、红”，便能找到包含端点的匹配组。如果换上来的是绿棋，又没有特殊道具交换或放宽条件，程序恢复原登记，再由后续流程处理无效交换表现。

这里的“冻结匹配组”是先保护已经认定的组，避免交换表现尚未结束，其他下落就改写这些格子。后续消除阶段还会重查匹配；试换成功不等于立刻逐格删掉。

怎样识别三连、四连、五连与2×2

匹配内核先收集小形状，再把它们组合成更大的候选。它不是从某颗棋出发，把所有相连同色棋都一口气消掉的“连通区域填充”。参与搜索的格子要有普通颜色棋、通过覆盖物与在途阻挡检查；要求排除下落棋时，还会检查棋子的CurrentCell与NextCell是否相同。［B3］

    把通过状态检查的小形状加入temporary

已经看见三连，为什么有时要等一下才消除

“识别出形状”和“此刻可以自动引爆”是两次判断。匹配组要求每格棋子都准备好：没有正在交换、下落状态稳定、预留计数小于1。然后每列取组内最高的一颗，再检查上方的Target里有没有同色棋子正在加入。［B4］

在“上方Target是同色、但上方棋子还在下落”的分支中，程序比较当前关卡时间与下方这颗棋子的状态改变时间＋0.25秒。正常有限时间值下，当前时间不晚于这个阈值就继续等待；不是每次发现匹配都统一延迟0.25秒。上方已经稳定时，还可能递归检查上方匹配组或继续向上检查。

例子：下方匹配组最高棋子的状态在关卡时间10.00秒改变，上方又有同色棋正落入。该分支在10.20秒、10.25秒仍要求等待；到10.26秒，这条时间条件不再要求等待，其他准备条件仍要通过。这里用的是关卡时钟，不是网页或系统墙钟。

【体验解读】这类等待给正在加入的同色棋保留合并机会，可能让玩家看到一次更完整的组合。它也解释了“颜色已经连上，为什么没有立刻炸”；具体体感延迟还要结合动画、格子冻结与其他调度，不能把0.25秒当成所有连锁的固定间隔。

GetNextItemOfCell不是简单读取Current：它读取Next，询问棋子是否允许落向目的格，还要求棋子没有另一个目标，或其Target仍是原来源格。自身Next登记的处理位于冻结检查之前，说明“被冻结”也不能被改写成这个函数完全不处理任何登记。

例子：两颗棋子正在接连下落时，下一段落点可能已经预订。按Current颜色数组从上往下搬运，会漏掉这些在途关系，导致棋子重叠、跳格或同一颗被多个空格领取。原代码先规划登记，再由运动组件推进，这两步需要分开还原。

斜落：先检查落点，再检查通路和来源棋子

斜落就是上方的棋子从侧面滑进空位。程序会先规划直落，再处理需要斜落的格子；它不会看到左上或右上有棋就立即搬过来。一次斜落要依次通过落点资格、向上搜索、对角来源、左右选择四层检查。［B7］

1. 这个空位是否需要斜落

CalculateCrossFalls只处理普通格，而且必须已被标记为需要寻找斜落来源、没有Target、也不属于下层棋盘。Target表示已经分配的下落目标关系：即使画面还是空的，只要直落规划已把A分给这个位置，就不再让B斜着抢进来。

for destination in 待处理格子:
    if not destination.IsNormalCell(): continue
    if not destination.shouldFindCross: continue
    if destination.Target != null: continue
    if destination.IsInBelowBoards(): continue
    FindCrossItem(destination)

2. 沿上方建立左右待检查位置，遇到阻断就停

FindCrossItem从落点开始逐格向上走。每到一个位置，依次检查：是否冻结、能否通行、是否被多个可下落物体瞄准、boardId是否仍与落点相同。任意一项失败，就停止继续向上收集。能否通行还会询问当前物体的IsAvailableForFall，所以不能只根据“这格有没有棋子”判断。

在非空白格，程序分别检查紧邻的左格和右格。某侧邻格被冻结，就停止收集这一侧；另一侧仍可继续。其余情况下把当前访问位置压入对应栈，后面再取它的左上或右上来源验证。栈里保存的是待查位置，尚未确认那里有可用棋子；左右两侧都停止后，向上搜索也结束。

清空左栈、右栈
leftOpen = rightOpen = true
visited = destination
while visited存在 and (leftOpen or rightOpen):
    if visited.IsFallFrozen(): break
    if not IsFallPossibleFromCellToCell(visited, null): break
    if visited.IsCellTargetedByMultipleFallableItem(): break
    if visited.boardId != destination.boardId: break

    if not visited.IsBlankCell():
        对左、右两侧分别处理:
            if 本侧已停止: 跳过本侧

位置是边向上走边压栈、之后再弹出，因此验证顺序还取决于压栈过程，不能直接理解为“从空位旁边最近的棋子开始找”。IsBlankCell是代码中的格子类型判断，也不能直接替换成“没有Current棋子”。

3. 从待查位置取对角来源，检查它是否真的能动

FindTargetItemFromCrossCell先检查落点缓存的下方关联格。如果它存在、非空白且没有下落阻挡，就读取该格Target棋子的NextCell和CurrentCell：至少有一个存在，且Y小于本次访问位置的Y，才继续探对角来源；否则本次候选失败。下方关联格不存在、为空白或有阻挡时，跳过这一项检查。这里比较的是代码坐标和在途登记，不能简化成“下方有空位就能斜落”。

below = destination.缓存的下方关联格

    moving = below.Target
    next = moving?.NextCell
    current = moving?.CurrentCell
    if not ((next存在 and next.Y < visited.Y)

例子：空位C的左上有A，但A所在格被冻结，A就不能成为斜落来源。即使A没有冻结，如果它已被分配到另一个目标D，也不能再让C领取它。玩家看见的是“旁边有颗棋没滑下来”，程序检查的则是“它现在有没有资格被这个空位使用”。

4. 合法候选之间怎样选左边或右边

通过资格检查之后，才进入左右挑选。左栈弹出的来源若是合法普通棋，立即选它；若是合法特殊道具，则还会检查右栈，合法的右侧候选可以替换它。右侧失败时，左侧特殊道具仍可使用。两边都没找到就继续弹栈，找到后先登记Target，实际移动由后续更新推进。

while 左栈非空 or 右栈非空:
    chosen = 验证左栈弹出的对角来源（栈空则为null）
    if chosen存在 and not chosen.IsSpecialItem():
        SetTargetItem(destination, chosen)
        return
    right = 验证右栈弹出的对角来源（栈空则为null）
    if right存在: chosen = right
    if chosen存在:
        SetTargetItem(destination, chosen)
        return

构造例子：左边是合法红棋、右边是合法蓝棋，这轮直接选左边；左边是合法火箭、右边是合法蓝棋，这轮选右边；左边是合法火箭、右边无合法候选，则仍选火箭。这段选择没有左右各50%的随机，也没有按剩余关卡任务评分。

冻结：格子暂时不参与新的下落规划

这里的冻结是程序暂时占住格子的下落资格。例如交换已找到一组可以消除的棋，但交换表现还没结束，就先保护相关格子；下落搜索遇到冻结检查时，不能继续按普通格处理它们。这样可以避免已经认定的匹配被另一颗落子提前改写。它指的是运行状态，不是关卡里的冰块障碍。［B8］

冻结次数大于0，就仍有人占用

同一个格子可能同时被多个操作占用，所以FreezeFall用计数而非开关：冻结一次加1，释放一次减1；IsFallFrozen只问计数是否大于0。两次冻结需要两次释放，先结束的操作只能撤回自己那一次。

FreezeFall():
    freezeCount += 1
    OperationStart(1)

UnFreezeFall():
    freezeCount -= 1
    OperationFinish(1)
    if freezeCount < 0:
        记录错误

IsFallFrozen():
    return freezeCount > 0
构造过程计数下落冻结检查
没有操作占用0通过此项检查
操作A冻结这个格子1仍冻结
操作B也冻结同一格2仍冻结
A结束，释放自己的一次1B还没结束，仍冻结
B结束，再释放一次0通过此项检查，继续检查其他下落条件

释放冻结不等于立即移动

计数回到0，只表示这一项限制已解除。下落还要检查阻挡、来源、Target和Next预订等条件；也不能据此断言已在播放的移动动画会被取消。若多释放一次导致负数，当前指令会记录错误，没有看到自动把负数改回0的处理。斜落还存在独立的冻结字段，不能把所有限制移动的状态都并为这一个计数。

多棋盘：同一关内，从一段棋盘切到另一段

多棋盘是一关里有多段棋盘，当前只操作其中一段，流程推进时视图转到另一段继续玩。例如可以把它想成一张分段展示的长棋盘：前一段结束后画面移到下一段，仍在同一关里。程序用boards[]保存各段，用CurrentBoardId记录当前段；这也解释了为什么下落搜索必须检查boardId，不能只按画面上的上下左右取棋。这个例子说明结构，不代表某一实机关卡的切换条件。［B9］

进入切换流程后，先锁输入，再移动棋盘

StartChangingBoard把IsChanging设为true，登记编号13的进行中操作，并禁用触摸。随后计算过渡时长，在时间0安排移动回调、在结束时间安排收尾回调，同时启动完成等待协程。起始回调用DOMove把棋盘移向传入的新位置，并使用传入的动画曲线；背景也有对应的滚动分支。

StartChangingBoard(newPosition, boardCurve, backgroundCurve, speed):
    IsChanging = true
    OperationStart(13)
    heightDiff = CalculateHeightDiffBetweenBoards()
    DisableTouch()
    duration = 0.3 + sqrt(heightDiff) * 0.32 * speed

这里的boardId是内部排列编号，减1表示转到下一段内部记录，不能理解成玩家关卡号倒退。ChangeBoard与画面移动是不同的方法；只移动视图而不更新当前段，或只改编号却不处理输入与在途落子，都不足以复现切换。

画面移动结束，与切换状态结束，是两个时点

结束回调先检查当前棋盘是否还有正在进入的物体；没有时调用AllowRefillOnNewBoard，允许新棋盘补入。随后结束编号13的操作、重新启用触摸，并通知切换完成事件。另一个协程持续检查HasAnyOperation：只有没有任何进行中操作时，才调用CompleteChangingBoard清除IsChanging，并恢复对应的镜头方向控制。

构造例子：棋盘移动到位时，如果另一个操作仍未结束，收尾回调已经可以重新启用触摸，但IsChanging仍会保持true，直到等待协程看到所有操作结束。能否实际接受某次交换还取决于其他输入门槛，不能把EnableTouch直接等同于“所有操作立即可用”。切换状态也不能简单在固定秒数后无条件清掉。

高度差影响移动时长，触发切换的条件要分开看

公式是0.3＋√heightDiff×0.32×speed。例如给定heightDiff=9、speed=1，得到1.26秒；heightDiff=16时为1.58秒。这是给定输入的计算例子，不是某关实测；speed是传入参数，不能直接当成玩家倍速。高度差、动画结束、其他操作结束分别控制不同环节。

上述代码说明的是进入切换函数之后如何处理。究竟哪类目标、在什么局面下发起切换，仍要沿各调用入口核对；当前证据不足以统一写成“清完本屏所有目标就切换”。
