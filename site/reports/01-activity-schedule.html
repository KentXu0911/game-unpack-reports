结合各处出现的 fileDownloadManager + AssetBundle metaBundle + IsAllBundlesDownloaded()，这些活动具备运行时下载路径。但缺少同名本地 group 不能单独证明“纯远程”：仍可能共享资源、纯代码实现或超出当前扫描范围。 所以「解包能扫到」和「解包能拿到」是两件事——§5 清单里这两列分开写了。 反过来，另外 15 个是有本地资源组的（合计 97 个 bundle）： HiddenTemple(12) · PuzzleBreak(3) · DailyLightningRush(5) · TeamTournament(3) · InviteFriends(3) · RobotRivals(3) · RoyalWorldCup(7) · AncientAdventure(7) · ShortExpeditionEvent(19) · TrainJourney(6) · OceanOdyssey(13) · MergeSmith(2) · ClashOfChampions(4) · PropellerRush(4) · WeeklyPass(6)—— 29 个管理器在当前口径下分成 15 / 14；这是资源映射现象，不足以反推制作方的轻/重活动策略。
先说最重要的一条：客户端里没有任何绝对日期或时间戳。 对 decoded/config/ 全部明文配置做正则扫描，10 位 epoch 秒 = 0 命中， YYYY-MM-DD 字面量 = 0 命中。也就是说「哪个活动什么时候开、开到几号」这件事 在客户端根本不存在——客户端只持有结构基线（关卡结构 / 奖励梯度 / 资源清单）， 真正的时间由服务端在 GetXxxInfoResponse 里下发 （DynamicOffer.RemainingTimeInMs / IsRemainingTimeFinished / IsEventActiveInServer 就是这套下发的落点）。
那么甘特图怎么画才诚实？ 横轴换掉：用关卡进度当"时间代理"。每个活动的 GetUnlockLevel() 是客户端里 唯一确定、且能直接对应到玩家旅程的排期量。所以主甘特图的横轴是 L0→L100， 纵轴是 29 个活动，条的起点就是它的解锁关卡——这是硬的。 至于节日皮肤的月份窗口，那是从资源槽名反推的软推断，单独一张图并逐行标了证据等级。
通俗版 把游戏想成一栋楼：客户端只拿到了每个活动贴在几楼（解锁关卡）和每个活动长什么样 （资源包 + 奖励表），但电梯什么时候停哪一层是物业（服务器）每天说了算。 所以你能画出"活动什么时候你能看见"，画不出"活动哪天下线"。

§3 甘特图② · 节日主题节奏轴

客户端没有日历，但有节日皮肤。把 Theme 枚举（9 项）和 FeatureBundleType 里带节日名的资源槽（Halloween / BlackFriday / NewYear3·6 / Easter6 / Spring3 / Jungle / RoyalCup3·6 / TravelDeal ×4 城）拼起来，就能反推出 「这一年要过哪些节」——但只有主题名，没有月份。所以横轴的月份是按节日常识给的 可读区间，每行标了证据等级，请按等级使用。

证据等级怎么分的：
E1 Theme 枚举字面 + 对应 bundle 组双证（Halloween / Summer / Holiday / RoyalWorldCup / Default）
E2 只有 FeatureBundleType 槽位字面，没有对应本地 bundle （Jungle / BlackFriday / NewYear3·6 / Easter6 / Spring3 / RoyalCup3·6 / TravelDeal 四城）
E3 只有枚举字面、连资源槽都没有（Christmas / ValentinesDay / Diamond）—— 说明这几个节日的皮可能是运行时远程下载，也可能只是预留位
通俗版 这张图回答的是「这游戏一年打算过几个节」。从皮肤名字看至少 12 个： 万圣节、黑五、圣诞、新年、情人节、复活节、春季、夏季、暑期旅行（巴黎/罗马/伦敦/纽约四站）、 世界杯、钻石、以及每周的默认皮。但对不上"几月几号"——因为排期表在服务器手上。

§4 甘特图③ · 互斥轮换槽位

event_dependency_default_config.json 是整个包体里唯一一份 直接描述「哪些活动不能同时开」的文件：10 个 group，组内活动互斥。 橙色 = 组内有多个候选（真轮换），灰色 = 独占（占着位等下一个同名活动周期）。

这张表的价值和它的边界都要说清： 10 个槽位只覆盖 14 个 EventType（id 0–16），全落在旧活动家族。 id 17 以后的新活动（SkyRace / TeamTournament / MissionPursuit / MissionControl / LavaQuest / TrainJourney / OceanOdyssey / AncientAdventure / RobotRivals / MergeSmith / ClashOfChampions / PropellerRush / WeeklyPass / RoyalWorldCup / ShortExpedition / DailyRewards） 一个都不在里面。两种解释：①新活动的互斥规则搬到了服务端； ②新活动之间本来就不互斥。客户端的证据支持不了任何一个，需要抓包 GetUpcomingEventsInfoResponse 才能定。
另一个配套机制：跨活动 eventId 链。 几份配置里有成组的 *LastEventId 字段，用来把一串活动串起来：
· train_journey：ttoLastEventId / mcLastEventId / srLastEventId / kcLastEventId / ppLastEventId / madnessLastEventId / mcoLastEventId / smLastEventId / mpLastEventId = 100000（全部占位）
· dragon_nest：同名 6 个字段全部 = 0
这是「上一个同类活动结束 → 下一个接上」的接力棒，值就是被接的那个活动的 eventId。 100000 是"还没接过任何一次"的哨兵。
通俗版 把活动想成 10 个"摊位"。G4、G7、G8 这三个摊位有 2–3 个摊主排队轮着上； 剩下 7 个摊位是专属摊位。而 *LastEventId 是摊主之间的交接单—— "我这次收摊后，接我班的是谁"。这份配置只写了谁能和谁不能同时在， 没写谁哪天上。

§7 排期机制：谁在什么时候说了算

7.1 客户端侧（可验证）

① 门禁：ILockableEvent.GetUnlockLevel() → 关卡门槛（§2 的 15 个台阶）
② 图标显隐：EventLockManager.MinLevelToShowIcons = 5； PartiallyLockedLevelMaxDifference = 4（差 ≤4 关时显示"半锁"图标诱导）； LockableEventBundleAbOverrideMinLevel = 1
③ 互斥：EventDependencyManager + EventGroups（§4 的 10 槽）； 字段 isEventBlockedByEventDependency / shouldForceClaimByEventDependency
④ 优先级排序：ExtraEnteredEventPriority=10000 / ExtraReadyToJoinPriority=20000 / ExtraLockedEventPriority=30000 （已在玩 > 可加入 > 被锁）；MaxPrelevelShownEvents = 3（关前最多挂 3 个活动）
⑤ 回流：EventsReactivationManager.ReactivationMinLevel = 101； reactivation_levels_config.json 给了 90 个回流关，呈两段结构—— L231–L1005 密集段 30 关（231–235 / 261–265 / 301–303 / 351–355 / 401·402·405 / 451 / 501 / 551 / 601 / 655 / 751 / 801 / 851 / 901 / 1005） + L1201 起每 200 关取 x01、x05 共 60 关（1201 / 1401 / 1501 / 1605 / 1801 … / 12805）
⑥ 冷却：NecessaryTimeToJoinSecondEvent = 1800000（进第二个活动前需 ≥30 分钟剩余）

7.2 服务端侧（客户端只能看到接收端）

每个活动管理器都有一个 UpdateUserEventInfo(...) 或 UserEventInfoReceived(...)， 形参就是服务端下发的载荷：
BalloonRiseManager.UpdateUserEventInfo(int requestedEventId, GetBalloonRiseInfoResponse response, bool isSuccess)
DailyLightningRushManager.UserEventInfoReceived(Nullable<DailyLightningRushInfo> info, ...)
LavaQuestManager.UpdateServerEventInfo(Nullable<LavaQuestInfo> info)
DynamicOfferManager：EventId / RemainingTimeInMs / IsRemainingTimeFinished / Segment / MatchedEventId / IsDisabledByBackend
请求入口：GetUpcomingEventsInfoCommand（RequestType/ResponseType 成对）→ "接下来开什么"是问服务器的
结论（限 build 38174 的已扫描客户端表面）： 包体可以证明客户端具备哪些活动结构、本地依赖和部分解锁/互斥基线； GetUpcomingEventsInfoResponse 等接口说明实时开关、时间窗和分组至少有服务端输入。 但本次没找到绝对时间戳，不等于证明“全部活动纯服务端排期”； 也不能用这个包体保证覆盖新版本或实时下发的每一个活动。 要确认具体起止日期和当前活动，需抓取该账号的响应体，或做连续时序观测。

§8 长期活动 vs 限时活动

判定规则：能拿到的硬证据只有三条——① 是否在 event_dependency 互斥槽里 （在 → 轮换位 → 限时）；② 名称/配置里是否明写周期（Daily / Weekly / season）；③ 是否与 Theme 皮肤绑定（绑定 → 季节性）。三条都不沾的，标为「常驻」但证据等级较低。
