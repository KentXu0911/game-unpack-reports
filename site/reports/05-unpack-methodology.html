├─ 有 ──> 先做周期检测（自相关），不要先装 IDA

├─ 有 ──> ⭐ 第一优先级：这一张表能白拿物品表 + 活动模板库

判断规则（可当预判准则）：运营能随时调的数字 → 服务端；改了要发版的东西 → 包里，而且大概率明文。

2.2.4 为什么用 Python + capstone 而不是 IDA / Ghidra

本项目所有反汇编都用 capstone 在 Python 里做。收益有三：

  1. 可批量化、可复现。 IDA/Ghidra 是交互式的，42 条奖励代码 × 每条要跟 3 跳指针 这种活必须脚本化。
  2. 免许可证。 不用管 IDA 授权，也不受 Ghidra 的 JVM 启动开销拖累。
  3. 和索引产物同源。 反汇编结果直接落 CSV/JSON，和 HTML 报告共用一套真相。

代价是没有反编译器（只有反汇编），所以需要人读汇编。为此写了一个通用批注器（RM scripts/67_gating_chain.py），把每行反汇编自动补上人类可读的注释：

0x275dfd4  adrp  x8, #0x5199000
0x275dfd8  ldr   x8, [x8, #0x270]        ; slot 0x5199270
0x275dfdc  ldr   x1, [x8]                ; → "ULV"
0x275dfe0  bl    #0x1d063b4              ; → System.String::op_Equality
0x275dfe4  mov   w0, #2                  ; = 2
0x275dfe8  b     #0x275e95c

bl → 被调方法全名、ldr → 字符串、mov → 十进制。这个批注器是本轮最有复用价值的工具，任何"配置里的魔法值到底代表什么"的问题都能用它打开。

2.2.5 FlatBuffers schema 恢复

RM 的 14,500 个关卡是 FlatBuffers，但没有随包发 .fbs。恢复路径是"反着来"：

dump.cs 里 grep GetRootAsFTiled / GetDataTableSchema
→ 533 个 FlatBuffers 表访问器
→ 从访问器的字段读取顺序 + il2cpp.h 的结构体布局，倒推出 slot 顺序
→ 产出 indices/fbs_schema_recovered.cs
→ 用它在 decoded/text_fixed/ 上按标准 table_pos − soffset = vtable_pos 精确读取

外部队验：用这套 schema 去解服务端下发的 83 个关卡，与本地逐格比对 83/83 完全一致 —— 这既证明了 schema 正确，也证明了本地关卡不是过期数据。这是"用独立数据源验证自己恢复的格式"的范例，比任何内部一致性检验都硬。

需要 改系统 CA（抓包）bind-mount 覆盖信任库即可同样先要 root
需要 多 ABI / 多 API 版本建多个 AVD 并存得有多台机器
需要 多版本 APK 对照装 / 卸 / 换包，秒级每次手动
性能（尤其图形）慢，软件渲染更慢快
被反模拟器逻辑识别有风险（部分游戏会检测）无

结论：解包场景（要 root、要反复重置、要改 CA）→ 默认上模拟器。只有遇到「游戏有反模拟器逻辑」或「必须测真实性能」时才换真机。

2.3.3 Frida 详解：原理 · 地址 · 语义坑 · 采集协议

A · 它是什么，为什么非它不可

Frida 是动态插桩工具，两侧配合：

宿主（macOS）                          设备（Android 模拟器）
frida-python  ──── 把 JS 源码字符串 ────>  frida-server（root 跑）
▲                                          │
│                                          ├─ 在当前进程里起一个 JS 运行时
│                                          ├─ 暴露 Native API：读写这块进程的内存
│                                          └─ 装 inline hook（运行时改写指令流）
└────────── send(payload)  ←───────────────┘

它给的是三件静态分析永远给不了的能力：

能力典型问题本项目用例
读内存这个字段此刻的实际值是多少读 LevelRandomManager 的 difficultySeed@0x24、BasicUserData.Level@0x14
hook 函数这个方法被调了几次、参数是什么、返回什么102 个 hook 点，覆盖难度 / 次数 / 补棋 / 特殊块 / 障碍
调函数 + 写内存我想让它现在执行这一步（做实验）写 Level + 调 LevelLoad() 实现跳关

为什么 IL2CPP 游戏必须靠它：静态解包能告诉你「代码长什么样」，但拿不到「这一次实际走了哪个分支」。

证据：IsAnyCombo 静态看只是个判断方法，运行时调用 69 次、只有 3 次返回 1。这个分布 —— 也就是"它到底有没有真的触发" —— 只有运行时才有。只看静态代码，你会得出截然相反的结论。

B · 地址怎么算：base + RVA

设备上的实际地址 = libil2cpp.so 加载基址 + RVA
  • RVA（相对虚拟地址）来自 Il2CppDumper 的 script.json（约 17 万条「方法名 → RVA」）。不要硬编码绝对地址，硬编码换一个版本就全废。
  • 基址运行时取：Process.findModuleByName('libil2cpp.so').base。
🔴 RVA 与 ABI 强绑定：armv7 与 arm64 的 RVA 完全不同，字段偏移也不同（RM 实测：arm64 下 difficultySeed 在 +0x24，armv7 不是）。禁止混用，项目里还专门为此在两个 ABI 上各跑了一次 Il2CppDumper。

C · 注入前必做：RVA 校验（tools/frida/validate_rva.py）

原理：把设备内存里 base+RVA 处的前 16 字节，与本地 .so 文件同一虚拟地址处的 16 字节，逐条比对。

本地侧不能直接按文件偏移读 —— 要用程序头做 vaddr → 文件偏移映射：

# 遍历 PT_LOAD，找到覆盖该 vaddr 的段，换算成文件偏移
p_type  = struct.unpack_from("<I", data, off)[0]
p_vaddr = struct.unpack_from("<Q", data, off + 0x10)[0]
p_filesz= struct.unpack_from("<Q", data, off + 0x20)[0]
if p_vaddr <= vaddr < p_vaddr + p_filesz:
file_off = p_offset + (vaddr - p_vaddr)

D · 102 个 hook 点怎么写：表驱动，不是 102 段重复代码

// { n: 名字, r: RVA, f: 是否读 this 字段, a: 是否记参数, v: 是否记返回值 }
var DIFFICULTY_HOOKS = [
{ n: 'LevelRandomManager.SetSeed',            r: 0x2A30DEC, f: false, a: true,  v: false },
{ n: 'LevelRandomManager.GetDifficultyNext',  r: 0x2A31478, f: true,  a: true,  v: true  },
{ n: 'LevelRandomManager.NextBool',           r: 0x2A31008, f: false, a: false, v: true  }
];

统一的挂载引擎消化整张表：

function install(module, group, spec) {
spec.forEach(function (s) {
var addr = module.base.add(s.r);
try {
Interceptor.attach(addr, {
onEnter: function (args) {
var seq = RM.seq++;
this.__rmSeq = seq;
var payload = { group: group, thisPtr: args[0].toString() };
if (s.a) { var a = []; for (var i = 1; i <= 4; i++) a.push(args[i].toInt32()); payload.args = a; }
if (s.f === true) payload = Object.assign(payload, readDifficultyFields(args[0]));
emit('enter', s.n, s.r, payload, seq);
},
onLeave: function (retval) {
if (!s.v) return;
emit('leave', s.n, s.r, { ret: retval.toInt32() }, this.__rmSeq);
}
});
} catch (e) {
emit('error', s.n, s.r, { message: String(e) });   // 单点失败不拖垮整批
}
});
}

好处：加一个观测点只改一行数据；三个开关（f/a/v）按需控制日志体量；单个点 attach 失败被 try 捕获成一条 error 事件，不影响其余 101 个。

E · 三个必须知道的 Frida 语义坑

① args[0] 是 this，不是第一个参数 🔴

C++ 成员函数调用约定里，第一个寄存器放的是对象指针。所以：

onEnter: function (args) {
// args[0] = this（对象自身指针）
// args[1] = 真正的第一个参数
// args[2] = 第二个 … 依此类推
}

把 args[0] 当第一参数用，是"参数值看起来毫无规律"的常见根因。

② enter / leave 必须用同一个 seq 配对 🟡

因为 hook 可能递归、也可能多线程并发，返回值不能靠"下一条 leave"来猜。

onEnter: function (args) {
var seq = RM.seq++;          // 分配序号
this.__rmSeq = seq;          // 存到本次调用上下文
emit('enter', s.n, s.r, payload, seq);
},
onLeave: function (retval) {
emit('leave', s.n, s.r, { ret: retval.toInt32() }, this.__rmSeq);   // ← 用同一个 seq
}
注释里也写明了：enter / leave 必须共用同一个 seq，否则无法把返回值配回调用。

③ 读任何字段都要 try 包住 🔴

目标指针可能是 null、可能已被回收、可能根本不是你要的类型。一次未捕获异常就能让整个 hook 静默失效（而且不会报错，只是后面不再有事件）。

function safeS32(p, off) { try { return ptr(p).add(off).readS32(); } catch (e) { return null; } }
function safeU32(p, off) { try { return ptr(p).add(off).readU32(); } catch (e) { return null; } }
function safePtr(p, off) {
try { var v = ptr(p).add(off).readPointer(); return v.isNull() ? null : v.toString(); }
catch (e) { return null; }
}

F · IL2CPP 内存模型：字段不是直连的，要跳好几次

C# 对象在内存里的字段不连续摆放，中间隔着 klass 指针等元数据。每一次 +offset 读到的往往是指针，得再 .readPointer() 才能到真正的数据 —— 这就是"两跳解引用"。

本项目最典型的一条链（读当前关卡号）：

UserInventory 实例
→ +0x18  → CurrentUser        （第一跳，指针）
→ +0x18  → BasicUserData      （第二跳，指针）
→ +0x14  → Level              （第三跳，int32，终于到值）
var u  = FN.getCurrentUser();
if (u.isNull()) return null;
var bd = u.add(0x18).readPointer();          // 第二跳
if (bd.isNull()) return null;
var level = bd.add(0x14).readS32();          // 第三跳 → 真正的值
每一跳都要判 null。 少判一次，[null + 0x14] 直接触发 access violation —— 而这个报错信息里只会告诉你"访问 0x14 出错"，不会告诉你是哪一跳断的。
字段偏移从 dump.cs 里查（它直接给出 字段偏移 / TypeDefIndex / vtable Slot）。

G · 从 JS 调托管方法：必须先 il2cpp_thread_attach 🔴（本项目最贵的坑）

  • 症状：用 NativeFunction 调任何托管实例方法，一律报 Error: access violation accessing 0x10。实测 LevelManager.LevelLoad(0x205BB40) 和 GetDownloadedLevel(0x205D618) 的报错完全一致。
  • 诡异之处：同一个方法由游戏自己调用时，Interceptor hook 正常命中 → 说明地址没错、方法没找错。
  • 根因：Frida 的 JS 线程没有注册进 IL2CPP 运行时。IL2CPP 生成代码里要取 il2cpp::vm::Thread::Current()，拿到的是 null，紧接着去读 [null + 0x10]（拿 thread 上的静态字段基址）→ 必炸。
  • 修法：做任何托管 NativeFunction 调用之前，先跑这一段：
var dom = new NativeFunction(Module.findExportByName('libil2cpp.so', 'il2cpp_domain_get'),
'pointer', [])();
new NativeFunction(Module.findExportByName('libil2cpp.so', 'il2cpp_thread_attach'),
'pointer', ['pointer'])(dom);
// 之后 thread_current() 不再为 null
判据：如果报错固定是 accessing 0x10（小偏移、固定值），先怀疑线程没 attach，而不是怀疑偏移算错。偏移错通常报的是一个大而随机的地址。

H · RPC 不可用 → 把整条时序搬进 JS 🔴

这是本项目最关键的一个架构决策。

实测事实：

方向可靠性证据
宿主 → 脚本（recv）🔴 不可靠Frida 16.5.9 的 recv(callback) 是一次性的，只交付下一条消息（连发 5 条只回 1 条 echo）
宿主 → 脚本（改"收到后重新 recv"）🔴 仍然不可靠在 Interceptor 回调开始命中之后，回包整体中断 —— 日志里 17 条 rpc 全部在 hook 之前，hook 之后 0 条
脚本 → 宿主（send）🟢 始终可靠hook 回调里 send 正常，setInterval 里 send 也正常

→ 结论：不要设计「宿主逐条发命令、脚本应答」的交互协议。 把整条时序写成 JS 里的状态机，宿主只负责监听 send。

var PLAN = {
target: 4,
mode: 'poke',              // poke | setlevel | admin | readonly | pokestart | pokeflag
stepGapMs: 1500,
stepTimeoutMs: 180000,
watchCount: 5,             // 执行后轮询观察次数（看服务端会不会回滚）
watchGapMs: 4000
};

执行流：① 装载 hook（函数级 11 个 + 指令级 1 个）→ ② setInterval 轮询实例指针（实例只能在 hook 命中时拿到）→ ③ 实例齐全后按 PLAN.steps 逐步执行，步间等 stepGapMs → ④ 最后按 watchGapMs 轮询若干次，观察关卡号是否被服务端回滚。

⚠️ 指令级 hook 有代价：它会让 JS 线程整体停摆（setInterval 不再触发、后续 send 全无）—— 详见 §4-D11。
所以 PLAN.useInsHook 默认 false，只在确实需要时打开，且打开后不能再依赖定时器。

收益：宿主断连也不影响脚本跑完；日志顺序与真实执行顺序严格一致。

🔴 这里还有一个自残型坑：宿主用正则把 JS 里 PLAN 那一整块替换掉以注入配置。
而脚本注释里如果出现了同样的字面量示例，非贪婪正则会先命中注释里那一段 ——
结果是真正的赋值原封不动，脚本一直跑内置默认值。
表现极具迷惑性：「三次不同模式的实验，其实跑的是同一套参数」。
已改成匹配 var PLAN = { + 换行 + };，并加 count=1 强校验。

I · Frida 的第二个身份：改内存做实验

不只观测，还能写。跳关就是"写 + 调"的组合：

FN.setLevel  = new NativeFunction(base.add(0x219AA68), 'void', ['pointer', 'int']);
FN.levelLoad = new NativeFunction(base.add(0x205BB40), 'void', ['pointer']);
// 数据层：写 BasicUserData.Level（+0x14），再调 LevelLoad() 让游戏自己走加载流程

为什么"只写不调"不行：改了字段但游戏不会自动重新加载关卡，屏幕毫无变化 —— 看起来像"写失败了"。 为什么"只调不写"也不行：加载的还是原来的关卡号。

服务端可能把关卡号回滚（这本身是有价值的情报）→ 所以脚本里带 watchCount / watchGapMs 轮询观察。
能力边界：跳过去的关卡「能加载、不能玩」（棋盘数据 / 关卡状态不完整）—— 详见 §4-E2。别把"加载成功"当"跳关成功"。
副作用警告见 §4-D12（内存改值不跨进程重启，且会影响账号状态）。

J · 自动走棋：为什么必须按坐标，以及坐标怎么来的

游戏是 Unity 渲染的 —— 没有可访问的 view 树，你拿不到"第 3 行第 4 列的格子"这种元素。只能：

screencap 截图 → 识别棋盘在屏幕上的位置 → 算出 9×9 每个格心像素 → input tap x y

坐标必须实测，不能估 🔴🔴（calibrate_grid.py）—— 这是最容易毁掉整轮采集的一个点（详见 §4-D7）：

坑后果
写死行距（本项目曾用 110px）实测应为 ≈116px，4 行累积约 17px 偏差 → 读数看起来"正常"，但"自带三连"、合法走法虚报到 40+ 个 → 交换被大面积弹回
忽略教程提示横幅横幅出现时整个棋盘被下压约 50px（纯偏移），格心全部错位
用颜色分类格子橙色花朵（棋子）会被误判成土块

更稳的做法：以棋盘的「灰浆色」(147,167,217) 为签名求列缝 / 行缝，再等距重铺格心 —— 不依赖任何写死常量。格子分类也不要靠颜色，按「格内灰浆像素占比」判：占用槽位实测 7~16%，帘幕 / 土块面板恒 0%，两者零重叠。

标定完成后输出一张 overlay 图（把格心画在截图上）交人工确认「格心确实压在格子上」：

python3 tools/frida/calibrate_grid.py outputs/shots/cur.png --overlay /tmp/cal.png
对工具本身也要保持怀疑：本项目的自愈在两张已知正确的截图上逐格无差异，但实测驱动 3 步只有 2 步真实生效，第 0 行仍最不可靠 —— 属于显著改善而非完全修复。

play_moves.py 支持 --bias top|bottom|left|right 控制走法倾向 —— 目的是让每一轮采集的走法分布可控、可复现，而不是随机乱点。配合 --tag A/B/... 给每轮会话打标，事后能按标签切分。

K · 采集协议：用「行号区间」切日志，不要用「时间窗口」 🔴

这是本轮最重要的方法论之一。

做法后果
❌ 错--duration 60 采 60 秒，然后按时间戳切段动作被切到错误的段里
✅ 对按行号区间切段每次走棋的因果链完整

原因：hook 回调里 send 的顺序是可靠的，但时间戳会因主线程阻塞而抖动 —— 一次 1.8 秒的卡顿能把两个相隔很远的动作压到同一毫秒。按时间切，等于用一个不可靠的轴去切一个可靠的序列。

实现：analyze_moves.py --moves <moves.json> --log <jsonl> --md <md> --json <json> —— 按「每次走棋动作的前后 hook 事件行号」划段，而不是按 t 字段。

L · 两条最贵的误读 🔴

① 「日志行数变多了」不是成功信号。

跳关失败、游戏弹回主界面时，会重跑一遍初始化流程，同样产生约 1800 行噪音事件。 判成功要看内容（关卡号真的变了 / 目标方法真的命中了预期次数），不是看行数。

② 「方法返回 1」≠「业务真的发生了」。

方法调用次数返回 1 的次数结论
IsAnyCombo693只有这 3 次是真触发
IsCombo48534几乎全是噪音

必须同时看「调用次数」和「返回值分布」两个数，只看某一个必然误判。

M · 硬约束：这台模拟器上 Frida 只能 attach 一次 🔴

一次会话结束后再 attach 会失败。已知的恢复办法只有：

adb shell am force-stop com.dreamgames.royalmatch     # 重启游戏进程

由此推出一条作业纪律：每次 attach 之前，必须把所有要采的点一次性挂全。 不能"先采一部分，看看情况，再补挂另一批" —— 补挂时你面对的是一个没法再 attach 的进程，只能重启，而重启会丢失"已经玩到某个状态"的现场。

N · 最小可运行闭环

# 1) 环境（起模拟器 + root + frida-server + 版本对齐）
bash tools/frida/setup_android_frida.sh 16.5.9
# 2) 必做：校验 RVA（必须 9/9 一致）
$PY tools/frida/validate_rva.py
# 3) 挂 102 个点，落 JSONL
$PY tools/frida/attach_rm.py --out outputs/runtime_hook_X.jsonl --wait-il2cpp 60
# 4) 自动走棋（另一终端）
$PYI tools/frida/play_moves.py --moves 6 --tag A --bias top --log <jsonl>
# 5) 按行号区间切段分析
$PYI tools/frida/analyze_moves.py --moves <json> --log <jsonl> --md <md> --json <json>
$PY = .../python/versions/3.13.12/bin/python3（有 frida，无 PIL）
$PYI = .../python/envs/default/bin/python（有 PIL + capstone，无 frida）
本机两个 Python 各有各的包，装混了会互相顶掉 —— 详见 §4-A1。

2.3.4 mitmproxy + CA 注入：绕开 /system 只读

Android 7+ 只信任系统 CA。常规做法 adb remount 在多数镜像上会失败（dm-verity + vbmeta 写保护）。不要硬碰 /system，用 bind-mount 覆盖信任库：

H=$(openssl x509 -subject_hash_old -in ~/.mitmproxy/mitmproxy-ca-cert.pem | head -1)
adb shell "setenforce 0;
mkdir -p /data/local/tmp/cacerts &&
cp -a /system/etc/security/cacerts/. /data/local/tmp/cacerts/"
adb push ~/.mitmproxy/mitmproxy-ca-cert.pem /data/local/tmp/cacerts/$H.0
adb shell "chmod 644 /data/local/tmp/cacerts/*;
mount --bind /data/local/tmp/cacerts /system/etc/security/cacerts"

mitmdump --listen-host 0.0.0.0 --listen-port 8080 -w capture/rm_capture.mitm
adb shell settings put global http_proxy 10.0.2.2:8080

两个实测事实：

  • Unity(IL2CPP) 的流量同样吃这个代理，TLS 正常解开 —— 没有证书锁定。所以"Unity 游戏抓不到包"这个假设是错的。
  • 真正值得抓的不是资源，是服务端到底下发了什么。RM 抓包的有限样本中，difficulty / tryCount / testGroup / experiment 明文键为零命中。这是有范围的阴性观测，不能据此证明包内 43 段阈值表就是运行时权威，也不能排除编码字段、其他端点或账号分组。

2.3.5 报告侧自检：Chrome headless + PIL

报告生成后必须视觉复核，否则只有用户看得出问题。本项目的两次自查抓到的都是真问题：

  • SVG 橙色框文字溢出：!ShouldAddAutoDialogIfHasAutoDialogBefore() && hasAutoDialogBefore 超出框边界 → 框从 x=120 w=300 改 x=78 w=384，字号 11.5 → 11。
  • 表格一整列显示「—」：价格读错了来源（见 §4-F3）。

无头模式的坑：--headless 下页内锚点跳转不生效，两张"不同锚点"的截图会字节数完全相同（10981 B），容易误判成"截好了"。解法是用裁剪副本（把目标章节单独存成小 HTML）或整页 --window-size=1440,16000 截后再用 PIL 裁切定位。

2.4 本机没装、需要绕的工具

实测 frida / adb / apktool / jadx / mitmproxy / aapt2 都不在 PATH（frida 与 mitmproxy 以 Python 包形式装、adb 在 SDK 里），unzip / java / python3 / node 可用。

缺的工具影响绕过方案
apktool二进制 AXML 解不了（AndroidManifest.xml）版本/权限从 XAPK 的 manifest.json 或 .apkm 的 info.json 取；真要看 manifest 就单独装 apktool
jadx看不了 classes*.dex业务逻辑本来就不在 dex 里（在 libil2cpp.so）；域名搜索直接对 global-metadata.dat 做二进制检索更快
aapt2拿不到资源 ID 表用 UnityPy 直接读 resources.assets

TypeTreeGeneratorAPIRM 的 MonoBehaviour typetree 读不出（UnityPy 1.25.3 缺 2021.3.55f1 类型树，报 Expected to read N bytes, but only read M）GH 那边是从公开 Git LFS 拿到了 2022 的类型树；RM 这条路当时没走通，改用 Il2CppDumper 的 il2cpp.h 还原结构体替代
一般规律：UnityPy 缺 typetree 时有两个方向 —— 补类型树（下对应 Unity 版本的类型树资源）或绕类型树（用 Il2CppDumper 恢复的结构体 + FlatBuffers schema 手工读）。前者一劳永逸但要找到版本匹配的资源，后者更可控但要自己写布局。

3. 七步 SOP：拿到新 APK 的第一个小时

Step 0 · 侦察（30 分钟，不写一行代码）

确认四件事，写进 README.md 头部：包名、版本/versionCode、引擎、容器形态。

搜索 包名 apk 一般能在 appgoblin / apkder / apkmirror 拿到"引擎 + 体积 + 版本"。

不要跳过这一步去写解包脚本。 引擎判错（Unity vs Cocos vs UE）会让后面几小时全部作废。

Step 1 · 拆包与校验

sha256sum pkg.xapk                       # 记进 README
unzip -o pkg.xapk -d bundle/
ls -R bundle/ | head -50                 # 看清有几个 split、哪些 ABI

算哈希不是形式主义 —— 后面任何"这个文件里没有 X"的结论，都必须绑定到一个确定的样本哈希上。

Step 2 · 引擎与结构判定

ls bundle/*/lib/*/                       # 有 libil2cpp.so → Unity IL2CPP
# 有 libcocos2djs.so → Cocos
# 有 libUE4.so → UE
ls bundle/*/assets/bin/Data/Managed/Metadata/global-metadata.dat
ls bundle/*/assets/aa/catalog.json       # 有 → Addressables
find . -name "*.bundle" -o -name "datapack*" -o -name "*_bundle_config.json"
find . -name "Lua*" -o -name "*.lua"     # 有 → xLua / Lua

→ 到这里就应该能回答 §1.5 的三条判断。

Step 3 · 跑信噪比最高的那一招

按引擎选，只跑一个：

情形第一招为什么
有明文本地化表导出 + 按前缀聚类白拿物品表 / 活动模板库，收益最大
有大量 MonoBehaviour全量 read_typetree() 扫描GH 实测 20,641 个 0 失败，信息密度最高
纯 IL2CPP 无明文配置Il2CppDumper → dump.cs grep 类名没有别的入口

这一步的产出物：一张对象/类清单 CSV。先读清单再决定提取策略，不要一上来全量导出。

Step 4 · 静态索引

把清单里命中的东西批量落成 CSV/JSON，不要一事一议。产物命名要能自解释（indices/xxx.csv）。

这一步就要开始写"证据列"：每行标 source / verified / evidence（见 §5.1）。

Step 5 · 语义回填（反汇编）

清单能给"有什么"，给不了"是什么"。语义靠反汇编：

配置里的魔法值  ──dump.cs 找对应枚举──> 枚举成员名
──stringliteral.json 反查──> 字符串字面量
──script.json 找方法 RVA──> capstone 反汇编 → 批注器

通用三项技术（RM 验证过，见 §4-C）：

  1. 两跳解引用：adrp → 元数据槽 → ldr 取 Il2CppString* → op_Equality 比对 → 得到枚举值。
  2. 跳转表：sub w8, wX, #1; cmp w8, #N; ldr x8, [x9, w8, sxtw #3]，表项直接就是字符串指针。
  3. vtable 偏移：偏移 = 0x138 + slot × 0x10，与 dump.cs 的 Slot: 号完全对应。

Step 6 · 运行时确认（只在静态说不清时上）

静态能给出"代码怎么写"，给不出"实际跑了哪条路"。三种情形必须上运行时：

情形手段
某段逻辑的分支条件取决于服务端值抓包（mitmproxy）看服务端下发什么
某个 hook 到底命中几次、参数是什么Frida Interceptor.attach
某数值实际随时间/状态怎么变Frida + 定时截图双证据

三步纪律：

  1. 先校验地址（RVA 逐条比对字节）
  2. 先跑基线会话（不改任何东西，确认 hook 会命中）
  3. 事件归属用日志行号区间，不用时间窗（见 §5.3 ③）

Step 7 · 产出与自检

  • 报告 HTML 生成后 html.parser 查标签平衡 + Chrome headless 截图视觉复核
  • 多份产物（HTML / JSON / CSV）做一致性审计：同一个数字在三份里必须一致
  • 写"未拿到部分的诚实清单"（§7），这是交付底线

4. 问题分册

每条格式：编号 · 现象 → 根因 → 修法。
标 🔴 的是"会让你得出错误结论"的，🔴 比 🟡 严重得多。

A 环境与工具类

A1 · Python 环境分裂（两个 Python 各缺一半） 🟡

  • 现象：装上 frida 之后 PIL 没了；装上 PIL 之后 frida 没了。
  • 根因：本机有两个 Python —— binaries/python/versions/3.13.12/bin/python3（有 frida，无 PIL）、binaries/python/envs/default/bin/python（有 PIL + capstone，无 frida）。
  • 修法：按用途分工，别混用。
    • 注入/附加/走棋：3.13.12/bin/python3
    • 截图处理/反汇编：envs/default/bin/python
    • 在脚本里写死绝对路径（P 与 PYI 两个变量）。

A2 · ModuleNotFoundError: No module named 'capstone' 🟡

  • 现象：用 /usr/bin/python3 跑反汇编脚本直接失败。
  • 修法：改用 binaries/python/envs/default/bin/python（capstone 5.0.7）。

A3 · tpk_ar 装不上，拖垮整个 UnityPy 🟡

  • 现象：pip install UnityPy 报 EEXIST: file already exists，换 TMPDIR 无效。
  • 根因：tpk_ar 只有 sdist，pip 建临时目录时冲突。
  • 修法：手工铺包。
pip download --no-deps --no-cache-dir -d ./whl UnityPy lz4 brotli Pillow \
    texture2ddecoder etcpak astc-encoder-py fmod_toolkit fsspec attrs
curl -sL -o tpk_ar.tar.gz <pypi sdist url> && tar -xzf tpk_ar.tar.gz -C src
cp -R src/tpk_ar-*/tpk_ar <site-packages>/
# 手工建 tpk_ar-0.2.4.dist-info/{METADATA,WHEEL,top_level.txt,RECORD}
pip install --no-deps --no-index --find-links ./whl UnityPy lz4 brotli ...

A4 · 缺 pyfmodex 伪装成"纹理格式不支持" 🔴

  • 现象：解析某个 bundle 时整个失败，报错提到图片/纹理。
  • 根因：pyfmodex 是在解析 AudioClip 时被 import 的；它缺失会让整个 bundle 解析循环抛出，栈里最先看到的是纹理相关调用。
  • 修法：pip install pyfmodex archspec texture2ddecoder（archspec 是 pyfmodex 的间接依赖，也得装）。
  • 教训：报错位置不等于出错原因。看到"纹理不支持"时先确认依赖是否装全，别急着研究纹理压缩格式。

A5 · ABI 不匹配装不上包 🟡

  • 现象：INSTALL_FAILED_NO_MATCHING_ABIS，AVD 的 abilist32 为空、native.bridge=0。
  • 根因：AVD 是 arm64-v8a，而 APK 只带 armeabi-v7a（APKPure 的 XAPK 常只给一个 ABI）。
  • 修法：换包，不换模拟器。去 APKCombo / APKMirror 找含 config.arm64_v8a.apk 的版本。

A6 · x86_64 镜像在 Apple Silicon 上不可用 🟡

  • 现象：想走 x86_64 路线，模拟器起不来或极慢。
  • 根因：M4 Pro 主机的模拟器只自带 qemu/darwin-aarch64，跑 x86_64 镜像需要 QEMU 全指令翻译。
  • 修法：放弃 x86_64 路线，直接用 arm64-v8a 镜像。

A7 · /system 只读，CA 装不进去 🟡

  • 现象：adb remount / adb disable-verity 均失败（dm-verity + vbmeta 写保护）。
  • 修法：setenforce 0 后 bind-mount 覆盖信任库，不碰 /system。完整命令见 §2.3.4。

A8 · AVD 不是 google_apis 镜像 → adb root 不可用 🔴

  • 现象：adb root 报 cannot run as root in production builds。
  • 根因：这是镜像类型问题，不是设置问题。带 Google Play 的镜像是 production build，永不可 root。
  • 修法：AVD 必须用 google_apis 或 AOSP 镜像（PlayStore.enabled=false）。

A9 · AVD 内存 < 4 GB → Frida 注入失败 🟡

  • 现象：注入报 unexpected crash while trying to allocate memory。
  • 修法：AVD 内存设 ≥ 4 GB。但注意 A10/D6：这个报错的根因不止内存一个。

A10 · 这台模拟器上 Frida 只能 attach 一次 🔴

  • 现象：第一次 attach/detach 完成后，后续 attach 一律失败，报同一个 unexpected crash while trying to allocate memory。实测连续探测 40 次全败（耗时 120s）。
  • 最危险的地方：attach_rm.py 的失败路径不抛异常（只打印"超时仍未看到 libil2cpp.so"就继续），很容易被误读成"采集成功但没事件"。
  • 修法：
    1. 看 jsonl 行数，不看进程是否退出。
    2. 只有 am force-stop 重启游戏才恢复；重启后第 1 次 attach 稳定成功。
    3. 结构性后果：jump_run.py（跳关）+ attach_rm.py（采集）这种"两次 attach"的用法必然失败 → 必须合并成一个 session（combo_run.py 在同一 session 上 create_script 两次，A = 跳关、B = 采集）。

A11 · BSD grep 的 BRE 交替静默失败 🔴

  • 现象：grep -nE "A\|B" 返回空（不报错），极易读成"库里没有 X"。grep -nE "class ShopPackageConfig" 也落空，因为声明写的是 public struct。
  • 修法：（a）用 grep -E（ERE），不要混 BRE 的 \|；（b）优先用工具级 Grep；（c）先 grep -c 关键词 确认真存在，再取行号。

A12 · 下载站点出口限制 / Cloudflare 🟡

  • 现象：apkmirror.com / apkpure.com / github.com 返回 000（SSL_ERROR_SYSCALL），走不走代理都一样；d.apkpure.net / apk4all 等返回 403。
  • 根因：本机网络出口是白名单制的，不是沙箱问题。
  • 修法：不要反复试 curl。要么让用户从外网机器下载后给本地路径，要么用 agent-browser（真 Chromium，能过 Cloudflare）。pypi.org / api.github.com 在白名单内，装 Python 包不受影响。

B 静态解析类

B1 · 关卡二进制"四轮作废"：真因是有损编码，不是格式特殊 🔴🔴（本次最贵的一条）

  • 现象：
    1. 全量提取报"命中 6,072 / 14,500（41.9%）" → 大量命中其实是 FlatBuffers 的 uoffset 向量（元素 0 = 空引用/邻近表相对偏移），天然"主导值为 0、值域小、长度整齐"，形状很像棋盘。
    2. 收紧判据报"可信棋盘 54 关" → 逐一检查颜色覆盖，42/54 连 1–4 四色都凑不齐。
    3. 用实机截图确证关卡 1 后，仍报"全量提取不成立"（全量仅 473/14,500 有候选）→ 这一步的判断本身也是错的。
    4. 「vtable 反查零命中」「棋盘数组起始偏移是奇数，4 字节对齐的 uoffset 数学上指不进去」→ 被当成"格式特殊"的证据。
  • 根因：有损导出脚本 02_unity_scan.py 用 UnityPy 读 TextAsset 的 m_Script 得到的是 Python str（UnityPy 内部用 utf-8 + surrogateescape 解码原始字节），脚本转回字节时用了有损的 .encode("utf-8", "ignore") —— 凡触发 surrogateescape 的字节被直接丢弃。

关卡 1 因此从真实的 4,200 字节被削到 3,495 字节（丢了 17%），之后所有偏移全部错位。

  • 修法：改用对称的 .encode("utf-8", "surrogateescape") 重新导出（decoded/text_fixed/），标准 FlatBuffers table_pos − soffset = vtable_pos 算法一次性打通。同算法扫全部 14,500 关：100% 成功，0 失败。
  • 两条方法论结论：
    1. 外部真值比内部一致性检验值钱 —— 没有 schema 时，统计启发式只能找到"形状相似的字节"，不是"有意义的结构"。
    2. 比截图更值钱的是先确认数据没被自己搞坏 —— 拿到 schema 后先花 10 分钟验证字节完整性，比花三轮调启发式判据便宜得多。
  • 资源读取结果：14,991份文本／二进制资源已无损读取，包括14,500关。非关卡数据应保留原始字节；字段语义与消费者行为仍需逐项确认。

B8 · 归档 datalen 断链 → 改魔数锚定；别用文件名链 🔴

  • 根因：不是 datalen 语义变了，而是大部分条目在包内已不是裸字节码 —— 第一个 entry 的 data 头是 4f 62 65 10，不是 \x1bLua（也非 zlib/lzma/gzip 魔数，压缩算法未识别）。5 个包 3,000+ 条目里只有 33 个是裸 Lua 字节码。
  • 修法：改用魔数锚定 + 三重自校验（名字后面紧跟 datalen 再紧跟 \x1bLua）：
for L in (m.start() for m in re.finditer(b'\x1bLua', out)):
    datalen = struct.unpack_from('<I', out, L-4)[0]
    for nl in range(3, 220):                      # 反推 <H namelen><name>
        p = L - 6 - nl
        if struct.unpack_from('<H', out, p)[0] != nl: continue
        name = out[p+2:p+2+nl]
        if not all(32 <= c < 127 for c in name): continue
        if not re.fullmatch(rb'[A-Za-z]\w*(?:\.\w+)+', name): continue
        # 三重通过 → data = out[L:L+datalen]
  • ⚠️ 千万别用"文件名链"（扫所有 <H nl><name> 自洽的位置）：Lua 文件内部的字符串常量（如 Data.Config.AdventureBoardScrollConfig_bandgirl）前面也带长度字节，会和真条目名混在一起 → 曾据此误判"config 复原了 3 条"。
  • 补充：若某包解出的 N 是天文数字，说明该包前面有额外头未对齐，但主体往往照样能解，别直接判定"这个包破不开"。

B9 · 包里存在「被去头的 Lua 块」，魔数锚定会漏 🟡

B10 · 加密类型不能靠类名判断 🔴

  • 根因：文件里有 DES 工具类 ≠ Lua 用它。 实际用的是重复密钥 XOR（周期 61）。回看：周期检测早已指向 61 周期流密码，块密码方向一开始就错了。

C 二进制语义类（IL2CPP 反汇编）

C1 · 配置里的缩写代码怎么解：两跳解引用 🟢（技术）

  • 背景：配置写 {"t": "ULV", "a": 15}。dump.cs 里 grep "ULV" 搜不到 —— 字符串字面量在裸 UTF-16 池里（stringliteral.json 共 28,426 条），代码只持有间接引用。
  • 技术形状：
adrp x8, #0x5199000 ; ldr x8, [x8, #0x270]   → x8 = 元数据槽地址 (0x5199270)
ldr  x1, [x8]                                 → x1 = Il2CppString*
bl   String.op_Equality ; mov w0, #N ; b      → N = 枚举值
  • 产物：42 条奖励代码 → RewardType 的完整映射，且正反双向独立还原、42/42 完全一致。

C2 · 判定顺序陷阱：ldr 的 disp==0 与 pages 表冲突 → 一条都解不出来 🔴🔴（本轮最隐蔽的一条）

  • 现象：脚本正常结束，输出"反汇编解出 0 条"，只剩 13 条硬编码常量兜底。不报错。
  • 排查过程（值得记住的排错姿势）：
    1. 打印函数头，发现约 42 组 adrp/ldr/bl 静态初始化三连（prologue）。
    2. 统计 bl 目标：0x1d063b4（String.op_Equality）×42 ⇒ 确认是 42 次比较。
    3. 确认 42 条 mov w0,#N 全部紧跟 b 跳到同一 epilogue ⇒ 确认形状没猜错。
    4. 手工探针直接解一次：slot 0x5199270 → 0x545df18 text='SNS' —— 链路本身是通的。
    5. 于是问题不在"链路"，在"我的模拟器没走到链路"。
  • 根因：ldr x1,[x8] 的 disp == 0，而 x8 同时也在 pages 表里（adrp 刚写过）。若把 base in pages 判在前面，会命中并算出 pages[x8] + 0，永远走不到解引用分支。
  • 修法：把 base in regslot 判定移到 base in pages 之前。
if base in regslot and mem.index == 0 and mem.disp == 0:      # ldr x1,[x8] → 取字符串指针
    s = slotstr(regslot[base])
    if s is not None: cur = s
    regslot.pop(dst, None); continue
if base in pages and mem.index == 0 and mem.disp >= 0:        # adrp 后的 ldr → 得到槽位地址
    regslot[dst] = pages[base] + mem.disp; continue
  • 修完 42/42 全部解出。
  • 教训："一条都解不出来"通常不是"库里没有"，而是"我的解释器走错了分支"。 遇到这种形态，先写一个手工探针证明链路可通，再回头查自己的模拟器。

C3 · 跳转表（switch）表项直接就是字符串指针 🟡

  • 背景：ToRewardTypeName 是反向函数，用跳转表把枚举值映射回名字。
  • 技术形状：sub w8, w19, #1; cmp w8, #0x34; adrp x9, #0x4f88000; add x9, x9, #0xc68; ldr x8, [x9, w8, sxtw #3]（表在 0x4f88c68，53 项 × 8 B，索引 = 枚举值 − 1）。
  • 第一次失败：把表项当作"需要再解引用一次的元数据槽"，得到 0 项。
  • 根因：解析 .dynamic 段的 RELA 重定位表（545,962 条）后确认 —— ELF 重定位已经应用过了（raw=0x544a7e0 直接落在字符串字面量区）。
  • 修法：s = SL.get(ent) or slotstr(ent)（先当直接指针，不行再当槽）。
  • 结果：42/42 正向 ↔ 42/42 反向，100% 一致（独立的第二套证据）。

D6 · 注入失败先做"系统进程对照测试" 🔴

  • 现象：unexpected crash while trying to allocate memory，看起来像内存不足（A9）。

D7 · 棋盘行网格不是常量（最容易毁掉整轮采集） 🔴🔴

D9 · recv(callback) 一次性 + hook 后 RPC 通道整体中断 🔴

  • 现象 1：诊断脚本连发 5 条 ping，只收到 1 条 echo（同期 setInterval 的 tick 每 3 s 正常 → 证明 JS 线程没卡）。
  • 现象 2：即使重挂载，宿主→脚本方向在 hook 开始命中之后仍会整体中断（日志里 17 条 rpc 全在 hook 之前，hook 之后 0 条）。
  • 修法：Frida 16.5.9 的 recv(fn) 只交付下一条消息，必须在回调里重新 recv(...)；但既然重挂载也不解决，最终放弃 RPC 模式，改成纯 send 单向 + 时序搬进 JS（rm_jump.js 的 PLAN 状态机）。send 方向始终可靠（hook 回调里、setInterval 里都正常）。

D10 · 从 JS 线程调托管方法必须先 il2cpp_thread_attach 🔴

  • 现象：任何托管实例方法（LevelLoad 0x205BB40、GetDownloadedLevel 0x205D618）都报 Error: access violation accessing 0x10；但同一方法由游戏自己调用时 hook 正常命中。
  • 根因：Frida 的 JS 线程没注册进 IL2CPP，Thread::Current() 得 null → [null+0x10]。
  • 修法：
var domainGet    = new NativeFunction(Module.findExportByName('libil2cpp.so','il2cpp_domain_get'),'pointer',[]);
var threadAttach = new NativeFunction(Module.findExportByName('libil2cpp.so','il2cpp_thread_attach'),'pointer',['pointer']);
threadAttach(domainGet());

加完之后 LevelLoad() 与 GetDownloadedLevel() 都能正常返回。

  • 判别要点："游戏自己调能命中、我从 JS 调就崩"这个对照本身就是诊断 —— 说明地址没错，是线程上下文问题。

D11 · 指令级 hook 会让 JS 线程整体停摆 🔴

  • 现象：在 LevelLoad 内部 0x205BC00（ldr w8,[x8,#0x14] 读 BasicUserData.Level）挂 Interceptor.attach 后，一旦执行到该地址：setInterval 停止触发、send 全无，而该 hook 自己一次都没进过 onEnter。

D12 · 内存改值不跨进程重启 + 账号状态副作用 🔴

5.3 六条硬方法论

① 先确认数据没被自己搞坏。 decode → encode 往返必须用对称的 error handler（surrogateescape 对 surrogateescape）。一个有损的 .encode("utf-8","ignore") 让 RM 关卡解析白费三轮。拿到 schema 后先花 10 分钟验证字节完整性，比花三轮调启发式判据便宜得多。

② 外部真值 > 内部一致性检验。 没有 schema 时，统计启发式只能找到"形状相似的字节"，不是"有意义的结构"。本项目最硬的两条验证都是外部真值：

  • RM 关卡 1 实机截图逐格像素比对 27/27 全等；
  • 服务端下发的 83 个关卡用恢复出的 schema 解码，与本地 83/83 完全一致。

③ 不要用时间窗推断事件归属，用日志行号区间。 自动操作每执行一步就记下前后的日志行号；日志严格按发生顺序追加，所以 [log_line_start, log_line_end) 这一段必定只属于那一步。这比"最近 60 ms 内命中了哪个池子"的时间窗猜测可靠得多（后者会跨段串味）。

④ 一个方法返回 1 不等于业务发生了。 活教材：

方法调用次数返回 1真实语义
ComboManager.IsAnyCombo693交换是否为一对道具 —— Combo 的触发条件，极稀少
ComboManager.Explode1—Combo 开始执行 —— 整个会话只进入过 1 次
ComboManager.IsCombo48534match group 是否含特殊块 —— 噪音极大，不能单独当判据

→ 可靠判据只有 IsAnyCombo == 1 且 ComboManager.Explode 被进入。 类似地，Combo 判定 与 Combo 执行 是两个分离阶段（交换被识别为道具对 → 延迟 148 ms 等动画落定 → 才进入 Explode）。

⑤ 判定"不可读"之前，先试 read_typetree()。 这是解包里性价比最高的一招。GH 用它把"dataconfig 加密不可读"翻成 20,641 个对象 0 失败。

⑥ 阴性结论要显式给出，并且值得花成本。 "服务端不下发动态难度参数"这个结论，价值不低于任何一个阳性发现 —— 它把一个开放问题关闭了。要得到一个可信的阴性结论，必须穷尽检索变体（见下节 §8 的关键词变体法）。

10. 一页速查：如果只能记住十条

  1. 先判结构，再动手。 catalog.json / Lua / 本地化表 三个有无，决定整条路线。
  2. 先怀疑自己，再怀疑格式。 decode → encode 必须对称；拿到 schema 先验字节完整性。
  3. 判定"不可读"之前先试 read_typetree()。 性价比最高的一招。
  4. "一条都解不出来"通常是解释器走错分支，不是库里没有。先写手工探针证明链路可通。
  5. 返回 1 ≠ 业务发生。 要求"判定 + 执行"双证据。
  6. 事件归属用日志行号区间，不用时间窗。
  7. 阴性结论要显式给出，并穷尽关键词变体证明。
  8. 外部真值 > 内部一致性检验。 一张实机截图、一份服务端数据，胜过三轮统计启发式。
  9. 报告三件事：生成后自检（标签平衡 + 截图）、多产物一致性审计、拿不到的诚实清单。
  10. 只能在可丢弃的小号上做内存改值实验。
一句话工作法：先判定结构 → 先跑信噪比最高的那一招 → 数据读不出来时先怀疑自己 → 静态解不动的才上运行时 → 每一步都留可复核的证据。
