# DynaDiff冷启动、完整失败与重试补查

样本 build 38174，原ARM64 libil2cpp.so 哈希见 verification.json。仅使用独立断网模拟器；原设备未修改。没有实际服务器响应，long是本地构造输入。

## 方法

A=81920；B=3470335148030（TryCount2=4095、DeltaMove=21、section=5、level=101）；A2回到81920。
每组冷启动前恢复同一份app_pFiles/shared_prefs，隔离外部Saves中的未结束棋盘。启动时GetLong读取DynaDiff的返回值替换为测试值，再由原恢复函数写入账号字段。恢复后同样将测试关号设为101。未改步数、最终seed或原玩法函数。
账户构造和恢复先于首页开局。点击Play，关闭Bird提示，读取棋盘，真实滑动/点击走棋。
A按提示坐标序列排序选操作，25步耗尽；B重放A操作，前12次操作前棋盘相同（即前11步后相同）。第12次是Tnt(40)+Propeller(10)交换，第13次操作前比较失败，未发送第13次重放输入。随后B使用自身提示策略走完剩余13步，因此分歧后的整局输出不可作为相同操作对照。
A/B均关闭续关报价，确认失败，Try Again，关闭教学，各做一次有效交换至24步；没有购买道具或步数。retry阶段各6次补棋值相同。初次/重试分别选seed371/741，不是人为固定。

## 结果与同值复测

初始棋盘观测字段、25步及seed一致。A/B各走完25步并完成失败和重试，流程没有异常退出。整局轨迹不一致，不能称为整局差分通过。
A2相同DynaDiff、相同seed重放第一步后也有一个格子不同，稍后再取快照差异仍存在。说明当前对照还不完全可重复；尚未分清时序、观察边界和未控制随机源。不能把A/B差异归因于DynaDiff，也不能由此证明DynaDiff没有影响。A2只作同值复测，没有完成整局。
棋盘快照只包括坐标、格子类型、填充类型、当前物体match/tiled/layer，未覆盖所有隐藏状态、格子附加层和随机流内部状态。

## 底层读取归属

0x102F22C位于GC扫描函数，gc-path.json记录从il2cpp_gc_collect到此函数的原字节直接调用路径；native.zip保存相关字节及汇编。函数引用Mark stack overflow字符串。gc-read.json记录启动时捕获的实际栈、读取值81920和不在对象地址范围的判断；移除进程地址、线程ID与时间戳。
该具体读取属于垃圾回收候选指针扫描，不是已识别的玩法状态解码。捕获此读取的多线程硬件监视随后停滞，整轮不得计为通过。

## 覆盖限制

完成运行使用部分getter/setter和玩法函数入口hook，不按调用线程过滤；并非监视所有线程的所有内存读取。零getter事件不代表零内联或别名读取。没有服务器写入前全程追踪，没有证明初始化所有缓存均受控，没有修改Easy/Hard表。
原局部函数实验仍保持原有边界。前次崩溃根因未定位，本次流程成功不等于定位或修复崩溃。

## 证据与复现

arm-a.json/arm-b.json/arm-a2.json是脱敏事件、动作和棋盘快照；verification.json有原私有日志哈希、比较结果和排除项。日志中的hits=0在无硬件监视运行里不是“无读取”证据。
probe.js保留本次仪器实现；host.py需要Frida16.5.9、adb与独立测试环境。默认--watch关闭；完成的运行不要启用--watch。复现需自行提供授权样本及相同私有基准存档（不公开账号数据）。reproduce-gc.py需capstone/pyelftools，在审计工作区按同路径运行，重算ELF异常帧函数边界与调用路径。
