手感参数：输入锁、结算节奏与补棋导演

拆包事实：手感不是一个单独的速度值，而是输入锁定、匹配结算、特殊块协程、补棋来源和反馈事件共同形成的时序。以下数字绑定 Royal Match build 38174；运行时窗口来自同版本模拟器 hook 摘要。

一手操作的状态链

选中／滑动→相邻格与方向判定→有效交换，Moves − 1→DisableTouch / 冻结→匹配、特殊块、障碍→下落与补棋→稳定后重新开放

原生路径能看到 GameTouchListener.DisableTouch 与后续 EnableTouch，特殊块创建协程末尾调用 MatchGroup.UnFreezeCells。这说明“动画期间不能继续操作”属于状态机，而不是只把按钮变灰。实机校准还确认有效交换会扣一步，并在稳定后替换顶部棋子。

交换最小滑动距离、采样频率、无效交换回弹和普通棋子真实移动时长，当前仍没有同口径的原端毫秒证据。

匹配与连锁的业务顺序

  1. CanAutoExplode 判断当前组能否自动爆炸。
  2. InitJellySpreadData、CreateCollectData、CreateSpecialItemData 先准备扩散、收集和特殊块保留格。
  3. 遍历棋子与静态物体的 TryExplode / ExplodeTopMostAboveItem。
  4. CreateSpecialItemForMatchGroup 启动特殊块出现协程；创建格保留，其余候选进入清除数据。
  5. DestroyTouchingItems 继续处理触碰目标，随后播放匹配爆炸与震动。
  6. 清除与下落完成后进入补棋，再开始下一轮匹配搜索。

这条顺序解释了为什么一个三消动作会有“确认—爆炸—扩散—补棋—再检查”的连续感，也解释了为什么把所有效果压成一个固定延时会丢掉原作的节奏层次。

补棋为什么既稳定又会变化

补棋入口先取上方已经排队的棋，再按列读取 FTiledPredefined 的 ItemModelQueue；只有这些路径没有返回结果时，才依次尝试目标列、普通随机集合和颜色回退。运行时摘要里的 61/66 队列命中与静态入口顺序相互吻合。

设计解读：队列让大多数补棋保持连续性；队列枯竭后，目标列、低匹配邻居过滤、普通随机和 GetDifficultyNext 才开始改变结果。这个“固定序列优先、随机回退兜底”的结构，是手感稳定性的主要来源之一。

给复刻工程的参数边界

配置键建议当前处理方式
input.swipeThreshold保留为待校准项；用同一棋盘逐步改变滑动距离与速度，记录提交、回弹、无响应。
state.touchLock随业务事件解除，不用一个总延时代替；至少区分交换、结算、补棋、稳定四个阶段。
cascade.activeWindowTargetMs先用 1,452–2,516ms 作为整体连锁窗口校准范围，再拆单个移动、爆炸和补棋时长。
refill.sourcePriority固定为 queue → predefined → target column → random fill → random color，并保留来源日志。
combo.propellerExtraDelaySeconds写入 0.02；只代表额外协程等待，不代表完整组合动画。

未确认与边界：交换判定阈值、真实棋子移动曲线、完整的 c 静态值、服务端难度如何改变候选权重，以及更多组合的跨帧等待仍需专门的实机捕获。客户端证据不能单独证明线上账号分组、实时热更或真实胜率。
