一个格子不只记录“现在有什么”

画面上的位置与程序预订的位置可能不同。下落规划至少要区分三个登记：Current是棋子当前所属格，Next是下一段移动要进入的格，Target是规划时分配的目标关系。格子和棋子两端都有对应关系，不能只用一张“颜色数组”表示移动中的棋盘。

例如，A正从上方落向空格C，B也在附近。画面上C还没被A占满，但A已经登记目标；后续规划不能直接把C当成可供B抢占的自由空格。反过来，清理旧目标也要保留已被Next预订的关系。［B1］

if not valid:

例子：一行原来是“红、红、蓝”，第三格下面有一颗红棋。把红棋换上来，临时逻辑行变成“红、红、红”，便能找到包含端点的匹配组。如果换上来的是绿棋，又没有特殊道具交换或放宽条件，程序恢复原登记，再由后续流程处理无效交换表现。

这里的“冻结匹配组”是先保护已经认定的组，避免交换表现尚未结束，其他下落就改写这些格子。后续消除阶段还会重查匹配；试换成功不等于立刻逐格删掉。

怎样识别三连、四连、五连与2×2

匹配内核先收集小形状，再把它们组合成更大的候选。它不是从某颗棋出发，把所有相连同色棋都一口气消掉的“连通区域填充”。参与搜索的格子要有普通颜色棋、通过覆盖物与在途阻挡检查；要求排除下落棋时，还会检查棋子的CurrentCell与NextCell是否相同。［B3］

temporary = []
for cell in 搜索范围:
    检查向右的同色三连
    检查向上的同色三连
    检查本格、上格、右格、右上格组成的同色2×2
    把通过状态检查的小形状加入temporary

possible = 小形状本身，以及可合并的两组三连
按PatternType从大到小稳定排序possible

for candidate in possible:
    if 任一组成小形状的格子已被其他组使用:
        continue  // 整个候选跳过，不裁掉重叠格后硬凑
    合并为匹配组，交点只加入一次

按扩展规则补入合格棋子
把组的归属写回各棋子

已经看见三连，为什么有时要等一下才消除

“识别出形状”和“此刻可以自动引爆”是两次判断。匹配组要求每格棋子都准备好：没有正在交换、下落状态稳定、预留计数小于1。然后每列取组内最高的一颗，再检查上方的Target里有没有同色棋子正在加入。［B4］

for cell in group:

        return false
    if 预留计数 >= 1: return false
    记录这一列组内最高的棋子

for topItem in 每列最高棋子:

        return false
return true

在“上方Target是同色、但上方棋子还在下落”的分支中，程序比较当前关卡时间与下方这颗棋子的状态改变时间＋0.25秒。正常有限时间值下，当前时间不晚于这个阈值就继续等待；不是每次发现匹配都统一延迟0.25秒。上方已经稳定时，还可能递归检查上方匹配组或继续向上检查。

例子：下方匹配组最高棋子的状态在关卡时间10.00秒改变，上方又有同色棋正落入。该分支在10.20秒、10.25秒仍要求等待；到10.26秒，这条时间条件不再要求等待，其他准备条件仍要通过。这里用的是关卡时钟，不是网页或系统墙钟。

【体验解读】这类等待给正在加入的同色棋保留合并机会，可能让玩家看到一次更完整的组合。它也解释了“颜色已经连上，为什么没有立刻炸”；具体体感延迟还要结合动画、格子冻结与其他调度，不能把0.25秒当成所有连锁的固定间隔。

GetNextItemOfCell不是简单读取Current：它读取Next，询问棋子是否允许落向目的格，还要求棋子没有另一个目标，或其Target仍是原来源格。自身Next登记的处理位于冻结检查之前，说明“被冻结”也不能被改写成这个函数完全不处理任何登记。

例子：两颗棋子正在接连下落时，下一段落点可能已经预订。按Current颜色数组从上往下搬运，会漏掉这些在途关系，导致棋子重叠、跳格或同一颗被多个空格领取。原代码先规划登记，再由运动组件推进，这两步需要分开还原。

斜落先筛候选，再决定左边还是右边

斜落只处理普通格、已标记需要寻找斜落、没有Target且不属于下层棋盘的格子。构建候选时沿上方检查冻结、可通行、多个可下落物体瞄准，以及boardId一致；遇到不满足条件就停止向上收集。非空白格还会把对应访问位置压入左右候选栈，之后逐个验证对角来源。［B7］

while 左栈非空 or 右栈非空:
    chosen = null
    if 左栈非空:
        chosen = 验证左栈弹出的对角来源
        if chosen != null and not chosen.IsSpecialItem():
            SetTargetItem(destination, chosen)
            return

    if 右栈非空:
        right = 验证右栈弹出的对角来源
        if right != null: chosen = right

    if chosen != null:
        SetTargetItem(destination, chosen)
        return

例1：左侧得到合法普通颜色棋，右侧也有棋——这轮直接使用左侧，不再探右侧。例2：左侧得到合法特殊道具，右侧也得到合法候选——继续探右侧，右侧可以替代左侧。例3：左侧特殊道具合法、右侧没有合法候选——左侧仍可使用。

这不是“左右各50%随机”，也不是“左侧永远优先”。这里解释的是两栈已建立之后的挑选段；栈中先验证哪个高度，还取决于之前的构建与压栈顺序。

对角来源还要通过可下落、可斜落、未冻结、目标未被另行分配等检查，并查看落点下方首个普通格的Target及其CurrentCell／NextCell高度关系。看起来左右都能滑入，不代表两者都已经通过完整资格检查。特殊接口和多格障碍的全部组合仍需逐类验证。

冻结用计数，避免一个动画提前放开另一个动画占用的格子

这部分可以直接对应到很短的原始指令。FreezeFall将格子偏移0x28的计数加1，IsFallFrozen返回计数是否大于0；解除时减1，负数会记录错误。斜落另有冻结字段，不能把所有阻止移动的状态合成一个布尔值。［B8］

// FreezeFall原指令节选
02ac9ba0: ldr w9, [x0, #0x28]
02ac9bac: add w9, w9, #1
02ac9bb0: str w9, [x8, #0x28]

// 等价的关键判断
FreezeFall:   count += 1; OperationStart(1)
UnFreezeFall: count -= 1; OperationFinish(1)
IsFallFrozen: return count > 0

例子：交换占用一次、消除表现又占用一次，计数从0到2。交换结束只减到1，仍不能落下；第二项也释放后才到0。如果用“任一动画结束就设false”，会让尚未处理完的棋子提前下落。

计算例子：只为展示公式，设heightDiff=9、speed=1，得到1.26秒；heightDiff=16时得到1.58秒。这些是给定输入的计算结果，不是某关实测时长。heightDiff单位与speed的完整输入来源、回调中何时恢复全部操作，仍需沿调用链核对，不能把speed直接当成玩家倍速。

【体验解读】匹配等待、冻结释放和切板禁触共同决定玩家什么时候能继续操作。只对上最终棋盘，仍可能出现连锁过早、棋子抢位或镜头尚未结束就能误触。它们与道具目标预订是不同系统：道具寻优页另行解释攻击选点、目标重选与在途攻击。
