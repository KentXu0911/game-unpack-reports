线索实际拿到的内容为什么值得查
DynaDiff账号里一个64位整数，以及读取、保存、同步和解码它的代码能解出尝试计数、关号、关卡段和步数差，可能用于记录玩法状态
动态难度配置表DynamicDifficultyEasy与DynamicDifficultyHard两份文件，按关卡区间配置尝试次数上下限字段名看起来与按玩家尝试情况调节难度有关，需要确认是否真的被玩法读取

目前只确认它们各自存在，还没有找到“读取DynaDiff → 查Easy／Hard表 → 改变棋盘”的完整链路。状态名、表名和方法名可以作为调查线索，实际作用要看后面的调用与实验。

它们分别是什么，与现有代码有什么关系

DynaDiff：一份可保存、可同步的账号状态

DynaDiff是同步时使用的键名，对应账号对象的DynamicDifficultyInventory字段。可以把它理解成一个小记录本：把几个数压进同一个整数，读取时再拆开。已恢复的内容有TryCount2、DeltaMove、LastUpdatedSection和CurrentLevel。这里的关号是记录内的关号，写入它不会直接切换关卡。

其中DeltaMove能解出“步数差”，是最值得追踪的字段。但能读出“多几步”，还需要另一段代码把它加到关卡步数上才会生效。当前已核对的普通关卡步数入口没有做这件事。

// 按原字节整理：DynaDiff的收发、保存与恢复。
收到响应中的 DynaDiff:
    替换账号.DynamicDifficultyInventory
    保存到本地键值表的 "DynaDiff"
    标记该键已同步
重启恢复存档:
    从本地 "DynaDiff" 读回账号字段
有该键的待同步记录时:
    把当前整数加入上传字典

这条链路说明客户端有能力接收并保留这份状态；收到后不会立刻原样再上传。联网测试中出现过本地 DynaDiff 从 0 变成 81920，但解码后的步数差仍为 0；尚未抓到服务器下发非零有效调整量的样本，见联网实测。“服务器可以写入”与“写入后会改变补棋”之间，仍缺玩法读取和应用它的连接。

动态难度表：按关卡段保存的尝试次数门槛

两张表分别叫DynamicDifficultyEasy与DynamicDifficultyHard。每一行记录一个关卡区间，以及Easy／Hard两侧的minTryCount／maxTryCount。例如101–120关，Easy列为34／60，Hard列为21／26。这些数是尝试次数门槛，不是给玩家增加的步数。文件里没有seed、颜色权重、飞机目标或补步数量。

两文件的Easy列逐行相同；Easy文件的Hard列全为-1，Hard文件部分关卡段有Hard数值。-1具体代表什么、计数按一关还是一段累计、超过门槛后该做什么，都需要找到读取和比较它的代码才能确定。

资源目录中登记了两张表，但没有找到确认的玩法消费者。目录登记只表示“能找到这个文件”。现有检查没有确认负责解析这些字段、比较门槛，再改变初始步数或随机种子的入口。DynaDiff的收发代码也不解析这两张表。

我们怎样检查它们有没有影响玩法

目前没有找到它们改变普通主线玩法的明确证据，但还不能彻底排除。已完成的局部对照没有变化；整局对照则没能稳定复现，不能算作排除成功。

两类线索的检查深度不同：Easy／Hard 两张表做了资源和代码追踪；DynaDiff 还做了断网改值对照和联网观察。下面按代码、局部对照、整局对照、联网实测分别说明。

1. 查代码：它们有没有真正接到玩法上？

对两张表，我们查找谁加载文件、谁读取尝试次数门槛，以及门槛满足后调用什么玩法逻辑。目前只确认资源目录里登记了文件，没有找到“读表 → 比较门槛 → 改变棋盘或步数”的完整调用链。因此只能说已查路径未见使用，不能说配置表不存在，也不能说已经证明它们永远不起作用。尚未做替换表内容的运行实验。

对 DynaDiff，我们追踪账号字段的读取和解码。它能保存、同步，也能解出“步数差”；但已核查的普通关卡步数函数直接返回原步数，没有把这个差值加进去。构造不同状态执行原函数，结果也相同。

2. 改值做局部对照：同一个函数的结果会不会变？

在断网测试副本的第 101 关，棋盘已经创建后，替换 DynaDiff，再恢复随机流等相关输入，调用原版函数作比较。这样检查的是：在同一局面、相同输入下，只改这份状态，结果是否变化。

局部对照：输入、输出和读取监视记录

在独立断网副本的第101关，使用原版已初始化的对象与函数，将DynaDiff换成不同构造值，再回到基准值。每次都恢复两条随机流的内部状态；检查seed时也恢复种子列表和管理器字段。没有把最终seed强制设为相同值。既有排列选取、重新生成并洗牌分别验证，完整排列逐项相同。

已完成的对照中，普通步数均输出25；seed均选中393；补棋序列和飞机单格选点序列分别逐项一致。针对账号字段的主线程读取监视没有在这些受控调用中命中，测试前后用原getter做正对照均能捕获读取。

因此可以说“这些入口在所测输入下未受影响”，尚不能说“证明开局配置和所有棋子生成永远不受影响”。改值时棋盘已经初始化；更早的开局缓存未被排除。这组局部函数测试后的重试异常退出，不能计作整局通过。独立冷启动对照与底层读取归属见下节。飞机也只测单格抽选，没有实际飞行、在途登记或扣层。

4. 联网实测：服务器响应、失败与重试时发生了什么

联网测试也做过，且捕获了成功的 Ping 和进度响应。它与上面的断网改值对照目的不同：断网实验主动替换 DynaDiff，检查函数是否受影响；联网实验不修改 DynaDiff 或服务器响应，观察服务端交互期间实际发生的变化。

场景实际完成DynaDiff 与玩法观察
新游客，第 1 关登录、读取服务器配置与 A/B 分组；断网恢复、恢复联网及联网重启DynaDiff 均为 0。后续存档恢复时，所测棋盘、剩余步数与补棋随机状态一致；这是未结束棋盘的恢复对照，不是全新开局对照。
第 1001 关实际耗尽 30 步、失败，再重试DynaDiff 保持 0；初始和重试均为 30 步，seed 从 180 换为 377。
第 5001 关，进度刷新抓到服务器进度响应并进入棋盘DynaDiff 从 0 变成 81920，但解码后的步数差仍为 0；开局 27 步。
第 5001 关，连续三次失败每局实际耗尽 27 步，均捕获失败事件，随后三次重试均完成进度同步DynaDiff 各次检查均为 81920；重试均为 27 步，seed 依次为 93、325、354。没有观察到有效难度状态调整。

81920 不是一次有效的加步调整。进度刷新期间，客户端先重置本地键值；原代码把步数差的原始编码写成 10，得到 81920 = 10 << 13。解码后 DeltaMove、尝试计数、关卡段和关号都为 0。运行中的更新序列与这条重置逻辑相符，但没有抓到服务器 DynaDiff 键携带非零有效调整量的样本。

这说明联网期间确实有服务器交互和本地状态更新；在这个账号的已测关卡与失败序列中，未观察到 DynaDiff 带来有效调整。不能据此排除其他账号、实验分组、更多失败次数或其他服务器机制。高关卡由新游客账号人工跳关得到，不能代替自然玩到高关卡的老账号；部分请求也出现 HTTP 400，不能称作所有网络服务正常。

三次连败时续关均显示 900 金币 +5 步；随后正常耗尽下一局，报价变为 +10 步，DynaDiff 仍为 81920。变化来自独立的续关弹窗计数，详见下一节。上述测试均未购买续关。

为什么出现差异，却还不能归因于 DynaDiff？

因为不改变 DynaDiff，重复同一组测试，也出现了棋盘差异。这说明对照环境还有未固定的因素。游戏除了补棋随机流，还有飞机等行为使用的普通随机流；即使固定两条初始 seed，匹配组洗牌和补棋也可能以不同顺序取走随机数。

例如，两件事共用一叠号码牌：补棋先拿一张、洗牌再拿一张，与反过来的结果可能不同。实际记录已观察到这种调用顺序变化，但导致先后变化的更早原因尚未定位。

因此，目前既不能把整局差异说成“DynaDiff 改变了难度”，也不能把前段一致说成“已经彻底排除”。进一步对照必须先让相同 DynaDiff 的重复实验稳定复现，再判断改值带来的差异。

整局对照：冷启动、重试与随机调用顺序的详细记录

在独立断网客户端上，两组都恢复同一份账号存档，隔离另行保存的未结束棋盘，再从首页进入第101关。基准值为81920，对照值为3470335148030，后者解码为关101、段5、尝试计数4095、步数差+21。替换发生在本地GetLong("DynaDiff")返回时，早于账号字段恢复完成和本次棋盘创建；它模拟的是客户端恢复不同状态，不是抓到并重放了服务器响应。

两组均不修改初始步数、不强制最终seed、不直接调用玩法函数。基准组用实际点击／交换耗尽25步；对照组重放相同操作，逐步比较棋盘。两组都正常进入失败结算，点击Try Again后重新得到25步，并各完成一次有效交换至24步。这证明本次完整失败与重试流程可以运行，也说明+21没有直接加到这两次开局步数上；不代表两组整局结果完全相同。

冷启动对照回执 · 方法、排除项与剩余缺口

补棋seed只管一条随机流，并不控制整局的全部随机行为。LevelRandomManager里另有一条普通随机流：开局时通过UnityEngine.Random.Range取一个数，再用它创建System.Random。在相同DynaDiff的三次启动中，补棋seed均选371，普通随机流的初始seed却分别为14705084、13964875、12351459。

原字节和运行记录都确认：FindSingleTargetCellForExploder从候选列表抽取索引时调用普通随机流Next；提示顺序和部分消除音效也使用它。所以只固定补棋seed，飞机的抽选输入仍未固定。这能解释原对照缺少了哪些控制变量，但不能据此断言每一次棋盘差异都由飞机造成。

固定两条初始seed仍不够，调用顺序也会改变结果。同值对照里，我们将普通seed控制为12351459，补棋seed由原逻辑选为371。快照改到游戏主线程读取；每步前要求下落停止、未完成操作清零、提示已就绪，并且棋盘连续至少1秒不变。两组第11步操作前的棋盘与补棋随机流内部状态都相同；随后第一次出现的随机调用差异，是下面这个顺序变化。

匹配组洗牌的链路是MatchGroup.ShuffleCells → ShuffleCellsBasedOnDifficulty → GetDifficultyNext；补棋也使用GetDifficultyNext。可以把它理解成两件事共用一叠号码牌：谁先取，拿到的牌就不同。这次已观察到相同DynaDiff下的调用顺序分歧；是什么更早的调度或隐藏状态导致先后变化，还没有定位。每步前等待稳定能避免把正在下落的棋盘当成结果，但不会固定一步之内每一帧的执行顺序。普通随机流在每次操作前的内部状态也没有完全对齐，不能称作全部随机状态一致。

改值对照目前只支持前段一致。同样控制普通seed后，将DynaDiff改成尝试计数4095、步数差+21，开局及前10步后的棋盘、步数与补棋随机流状态相同；第11步后的棋盘和随机状态不一致。本轮止于第11步，没有继续计为整局或重试通过。由于同值对照也出现分歧，目前无法把这项差异归因于DynaDiff。

分析提炼：目前可以采用的结论

分析层
DynaDiff已确认的是状态管理能力。收发、保存、恢复与字段解码可以复刻；所测普通玩法入口未使用它改变输出。当前没有足够依据把DeltaMove接到主线初始步数、seed或补棋权重上。
两张门槛表尚未找到有效接线。当前普通主线的资源、解析、策略与实机检查均未建立使用连接。“未启用或遗留配置”是据此作出的推断，不能当成它们过去如何使用、已经永久废弃的历史事实。
复刻时应把开局随机链与续关报价分开实现。重开换seed可以改变随机轨迹，已有证据没有证明越失败seed越容易；续关同价加量则有可见报价记录。不要用同一个“动态难度”标签把两者连成未经证实的因果链。

尚未确认与未排除的情况

边界层
还缺什么当前边界
真实服务器DynaDiff输入已抓到联网响应和进度刷新；本地 0→81920 解码后仍无有效调整。尚无服务器下发非零有效调整量的样本，后台触发规则仍未知。
从输入到完整开局、整局与重试本地恢复前改值的两组已完成开局、失败与重试；整局轨迹在道具组合后分歧，尚未证明整局一致。底层读取已归属垃圾回收；真实服务器输入、更早缓存及全线程任意读取仍未覆盖。
两张表的运行消费者未确定加载、计数口径、阈值比较、-1含义、方案选择及后续动作；没有改表对照。表覆盖范围的终点，也不能解释为此后自动交给服务器。
续关加量的自然触发条件受控失败样本能证明展示报价变化，不能给出所有账号的统一连败阈值、实际购买结果或与DynaDiff的因果关系。
真实胜率与更容易的seed还需固定关卡和求解策略，比较足够多seed的通关率与剩余步数；当前不能给任意seed贴Easy／Hard标签。

以上结论限定于本版已检查的普通主线路径与所测输入，不能扩展为所有账号、关卡、组合及版本都没有动态难度。进一步排除需要稳定的全线程读取监视、真实服务器输入路径，以及控制每帧调度和全部随机消费者后的整局对照。只固定补棋seed，或只固定两条初始seed，都不足以保证本次客户端逐步重放一致。
