难度状态：一个long里装了哪些数

原ExtractLong(state,start,end)取出含两端的位段；GetDeltaMove额外处理偏移编码。原值为0与原值为10，读出来都等于0。能解码出“步数差”，不代表主线会使用它。

整理代码：从难度long取字段
// 按原字节整理；位编号从0开始，范围含两端。
extract(state, start, end) = (state >> start) & ((1 << (end-start+1))-1)
tryCount2 = extract(state, 1, 12)
raw = extract(state, 13, 17)
deltaMove = (raw == 0) ? 0 : raw - 10
lastSection = extract(state, 18, 34)
currentLevel = extract(state, 35, 49)

实际策略与调用入口

分析提炼：表、状态与真正改变玩法之间还差一条链

分析层
Hard表能够完整拿到，但“101关启用Hard”尚未成立。从关101起，Hard侧出现非-1的阈值；这是配置事实。尚未找到这一版将它读入、判档并影响局内的完整消费者。默认资源也可能处于闲置路径；不能把未覆盖关卡直接解释为服务端必定接管。
这些阈值既不是逐关失败次数，也不是单调难度曲线。表按一段关卡配置min／max，区间长度会变化，上下限也有回落。它具体统计什么、何时比较、-1如何判断，需要实际消费者才能确定。不能据此说某关失败到阈值就必定放水。
代码里有两套TryCount，存储与调用并不相同。GetTryCount2读难度long；SemiDynamicDifficulty.GetTryCount则读PreLevelInventory里的另一段。后者由成功结算与首次显示续关的入口转入递增函数，排除League／Story，且只在关号不超过100时更新。仅凭名字不能把它们合并为“这关连败次数”。
当前这个主线路径没有读取DeltaMove来加初始步数。GetUpdatedMoveCount在非League分支直接返回传入步数；League另有加步。难度状态确实能从响应写入、保存和解码，但从“能存”到“改变主线步数”还不能画等号。
DifficultyNext是随机入口，不是动态难度判定函数。它把随机生成计数加一，再调用难度随机流的Next。初始颜色、补棋、洗牌等调用方会使用这条流；该函数自身不读Easy／Hard阈值，不检查失败次数，也不评价这个种子更难还是更容易。
