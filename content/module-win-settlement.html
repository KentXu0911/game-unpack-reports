目前查到的动态难度线索

包里有疑似难度状态 DynaDiff，也有 DynamicDifficultyEasy／Hard 两张配置表。我们沿着它们查了状态收发、玩法调用和运行结果：已测普通关卡步数、种子生成与选取、补棋、飞机单格选点，没有因替换DynaDiff而变化；两张表也没有找到接入这些玩法的代码。

失败重试后实际记录到的变化，是续关商品同价加量：同样900金币，展示步数由5步逐步增加到35步。它发生在付费续关报价里；现有证据没有把这项变化连到DynaDiff或两张难度表上。

扫描到了哪些疑似动态难度机制

事实层

配置来自包内TextAsset，逻辑来自同一build 38174的ARM64机器码与IL2CPP元数据。下文代码是按原字节整理的伪代码，保留原方法名；不是拿到了原工程C#源码。

线索实际拿到的内容为什么值得查
DynaDiff账号里一个64位整数，以及读取、保存、同步和解码它的代码能解出尝试计数、关号、关卡段和步数差，可能用于记录玩法状态
动态难度配置表DynamicDifficultyEasy与DynamicDifficultyHard两份文件，按关卡区间配置尝试次数上下限字段名看起来与按玩家尝试情况调节难度有关，需要确认是否真的被玩法读取

目前只确认它们各自存在，还没有找到“读取DynaDiff → 查Easy／Hard表 → 改变棋盘”的完整链路。状态名、表名和方法名可以作为调查线索，实际作用要看后面的调用与实验。

它们分别是什么，与现有代码有什么关系

DynaDiff：一份可保存、可同步的账号状态

DynaDiff是同步时使用的键名，对应账号对象的DynamicDifficultyInventory字段。可以把它理解成一个小记录本：把几个数压进同一个整数，读取时再拆开。已恢复的内容有TryCount2、DeltaMove、LastUpdatedSection和CurrentLevel。这里的关号是记录内的关号，写入它不会直接切换关卡。

其中DeltaMove能解出“步数差”，是最值得追踪的字段。但能读出“多几步”，还需要另一段代码把它加到关卡步数上才会生效。当前已核对的普通关卡步数入口没有做这件事。

// 按原字节整理：DynaDiff的收发、保存与恢复。
收到响应中的 DynaDiff:
    替换账号.DynamicDifficultyInventory
    保存到本地键值表的 "DynaDiff"
    标记该键已同步
重启恢复存档:
    从本地 "DynaDiff" 读回账号字段
有该键的待同步记录时:
    把当前整数加入上传字典

这条链路说明客户端有能力接收并保留这份状态；收到后不会立刻原样再上传。目前也没有抓到实际账号收到非零DynaDiff的服务器样本。“服务器可以写入”与“写入后会改变补棋”之间，仍缺玩法读取和应用它的连接。

DynaDiff字段、编码与同步入口证据

构造例：3470339186702解码为关101、段21、TryCount2为7、DeltaMove为3。这是核对编码的测试值，并非实际账号或服务器记录。

// 位编号从0开始，范围含两端。
extract(state, start, end) = (state >> start) & ((1 << (end-start+1))-1)
tryCount2 = extract(state, 1, 12)
raw = extract(state, 13, 17)
deltaMove = (raw == 0) ? 0 : raw - 10
lastSection = extract(state, 18, 34)
currentLevel = extract(state, 35, 49)

Delta原值为0与原值为10，解码结果都为0。下载独立解码工具。

待同步计数表示要上传的记录，不是失败次数。

动态难度表：按关卡段保存的尝试次数门槛

两张表分别叫DynamicDifficultyEasy与DynamicDifficultyHard。每一行记录一个关卡区间，以及Easy／Hard两侧的minTryCount／maxTryCount。例如101–120关，Easy列为34／60，Hard列为21／26。这些数是尝试次数门槛，不是给玩家增加的步数。文件里没有seed、颜色权重、飞机目标或补步数量。

两文件的Easy列逐行相同；Easy文件的Hard列全为-1，Hard文件部分关卡段有Hard数值。-1具体代表什么、计数按一关还是一段累计、超过门槛后该做什么，都需要找到读取和比较它的代码才能确定。

资源目录中登记了两张表，但没有找到确认的玩法消费者。目录登记只表示“能找到这个文件”。现有检查没有确认负责解析这些字段、比较门槛，再改变初始步数或随机种子的入口。DynaDiff的收发代码也不解析这两张表。

实际玩法入口：策略、开局计数和随机流各做什么

GetUpdatedMoveCount(moves):
    if activeLevel.IsLeague:
        return moves + leagueLevel.extraMoves
    return moves                 // 普通关卡没有加DeltaMove

OnLevelFail(): return             // 这个回调本身不调整难度

当前已查到的随机链是LevelTryCount → seedList选项 → System.Random → DifficultyNext → 补棋候选池。重开推进开局计数，从而换一条随机轨迹；这本身不代表换成了更容易的seed。DifficultyNext是随机数入口，不负责比较Easy／Hard门槛或判断连败。随机算法与颜色实抓见补棋与随机链。

我们怎样检查它们有没有影响玩法

先追踪文件与字段被谁读取，再用构造状态执行原字节，最后在已初始化的原版客户端做局部对照。两张表做的是资源与代码追踪；DynaDiff另外做了改值实验，两类证据不能混用。

检查对象怎么检查实际结果能支持到哪里
Easy／Hard配置表扫描资源引用、表名与字段、文本读取入口、策略构造及玩法回调只确认资源目录登记；没有找到解析门槛并应用到玩法的连接已查普通主线路径未见接入；没有做替换两表内容的运行对照

原端对照：只改变DynaDiff，尽量保持其他输入相同

在独立断网副本的第101关，使用原版已初始化的对象与函数，将DynaDiff换成不同构造值，再回到基准值。每次都恢复两条随机流的内部状态；检查seed时也恢复种子列表和管理器字段。没有把最终seed强制设为相同值。既有排列选取、重新生成并洗牌分别验证，完整排列逐项相同。

已完成的对照中，普通步数均输出25；seed均选中393；补棋序列和飞机单格选点序列分别逐项一致。针对账号字段的主线程读取监视没有在这些受控调用中命中，测试前后用原getter做正对照均能捕获读取。

因此可以说“这些入口在所测输入下未受影响”，尚不能说“证明开局配置和所有棋子生成永远不受影响”。改值时棋盘已经初始化；更早的开局缓存未被排除。初始开局前有一次尚未归属的底层读取；局部测试后的完整重试异常退出，整局和重试验证均未通过。飞机也只测单格抽选，没有实际飞行、在途登记或扣层。

失败重试后观察到的是：同样金币能买到更多步

在L39的受控失败重试序列里，价格一直是900金币，弹窗给步依次为5、10、15、20、25、30、35、35。准确说，是续关商品同价加量，单位步数变便宜了；没有观察到这一序列的金币价格下降。

这组记录为了尽快制造失败，先记录原始步数参照，再临时强制为1步；期间没有购买续关。样本前已有账号计数，不能把第一行当成新账号第一次失败，也不能由这张表推导“所有人连败几次开始加量”。

代码上，弹窗把两部分加起来：EgoManager套餐的基础步数，以及EgoExtraMovesHelper的附加步数。样本中基础始终是5，增加的是附加部分，最高记录到30，所以最终展示35。只读套餐基础字段，会漏掉玩家真正看到的加量。

// 既有L39记录中的报价组成；不是自然连败触发公式。
金币价格 = 900
展示续关步数 = 套餐基础步数 + 附加步数
            = 5 + (0、5、10、15、20、25、30、30)
            = 5、10、15、20、25、30、35、35

它让玩家在失败后有机会用同样金币买到更多续关步数，从而继续当前局面。这与下一局免费增加初始步数、补入更有利的棋子是不同的机制。目前没有证据把这条报价变化连到DynaDiff或Easy／Hard门槛表；也没有在这组记录中实际购买，不能写成已验证加步到账。

同局购买成功后继续购买的价格档位，以及账号实验选择的首档方案，见失败续关与续关价格与步数实验；它们与这里“退出后再重试，首档续关报价加量”的记录分开。下载报价记录CSV · 原记录路径与哈希 · 实验条件与边界

分析提炼：目前可以采用的结论

分析层
DynaDiff已确认的是状态管理能力。收发、保存、恢复与字段解码可以复刻；所测普通玩法入口未使用它改变输出。当前没有足够依据把DeltaMove接到主线初始步数、seed或补棋权重上。
两张门槛表尚未找到有效接线。当前普通主线的资源、解析、策略与实机检查均未建立使用连接。“未启用或遗留配置”是据此作出的推断，不能当成它们过去如何使用、已经永久废弃的历史事实。
复刻时应把开局随机链与续关报价分开实现。重开换seed可以改变随机轨迹，已有证据没有证明越失败seed越容易；续关同价加量则有可见报价记录。不要用同一个“动态难度”标签把两者连成未经证实的因果链。

尚未确认与未排除的情况

边界层
还缺什么当前边界
真实服务器DynaDiff输入没有确认的非零实抓样本，不知道后台是否、何时、按什么规则更新。
从输入到完整开局、整局与重试现有局部实验改值发生在初始化后；未排除更早缓存、其他线程和间接读取。开局前有未归属读取，完整重试异常退出，尚未通过。
两张表的运行消费者未确定加载、计数口径、阈值比较、-1含义、方案选择及后续动作；没有改表对照。表覆盖范围的终点，也不能解释为此后自动交给服务器。
续关加量的自然触发条件受控失败样本能证明展示报价变化，不能给出所有账号的统一连败阈值、实际购买结果或与DynaDiff的因果关系。
真实胜率与更容易的seed还需固定关卡和求解策略，比较足够多seed的通关率与剩余步数；当前不能给任意seed贴Easy／Hard标签。

以上结论限定于本版已检查的普通主线路径与所测输入，不能扩展为所有账号、关卡、组合及版本都没有动态难度。进一步排除需在稳定环境中，从状态写入之前开始追踪，覆盖初始化缓存、完整重试与整局结果。
